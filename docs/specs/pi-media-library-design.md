# 图片与表情素材模块开发方案

状态：草案 · 2026-11-18。已确认范围见[重构决策](pi-refactor-decisions.md)，其他模块见[开发索引](pi-based-meido-design.md)。以下接口与表名是建议实现，验收场景尚待执行。

## 模块职责

首版面向图片、静态表情和动态表情。图片库用于画图、改图、按消息找回原图；表情库用于收藏、按图包管理以及角色主动表达。普通图片和原创表情共用 Pi 工具 `generate_image`。例如“画个你生气的表情”沿用该角色的外观，加上“Q 版、生气、鼓脸”等当次要求，生成用途标为表情。接收、保留和发送动态表情属于首版；生成输出的实际格式以生图后端能力为准。

## 架构与接入点

| 组件 | 职责 |
| --- | --- |
| Pi 素材扩展 | 注册生图、收藏、查找和发送工具。根据对话选择动作，能够只回文字。 |
| Meido 素材服务 | 建议用 Node.js / TypeScript 模块承载图库界面与 Pi 共用的业务逻辑。收藏时核对来源消息，使用已保存素材时核对所属角色和目标聊天，维护原件、索引和版本。 |
| 渠道适配器 | 把消息附件转换为带账号、聊天、消息 ID 和附件序号的引用；负责取回原件、复用平台贴纸、上传媒体与回传发送结果。 |
| 本地任务执行器 | 从 SQLite 领取生图、下载、预览和可选标注任务。生图后端适配器声明文生图、参考图、编辑及任务查询能力。具体供应商和兼容版本待验证。 |

生图路径为“Pi → 素材服务建任务 → 生图后端 → 原件入库 → 渠道发送”。收藏路径为“来源消息 → 取回附件 → 原件入库 → 加入图包”。自然聊天模块先判断是否参与，随后按需要检索表情。渠道、Pi 与管理界面通过素材服务操作同一份记录。

## 数据模型

原件落在实例私有目录，SQLite 保存可查询的元数据。建议采用以下逻辑实体，便于独立验证权限、版本与发送状态。

| 实体 | 关键字段及约束 |
| --- | --- |
| 原件 | SHA-256、相对路径、MIME、尺寸、帧数。哈希唯一；缩略图可重建；保留动态原件。 |
| 素材及来源 | 稳定素材 ID、所属角色、原件哈希或平台引用、来源账号／聊天／消息／附件序号、创建时间、父素材 ID。生成图另存有效提示词、后端、模型、实际参数和参考素材 ID。 |
| 图包与条目 | 按角色整理素材，条目保存别名、画面标签及表达含义。同一素材可加入多个包，当前群的叫法可用于搜索排序。 |
| 聊天偏好 | 可为聊天设置优先使用的图包，分别设置允许主动发表情、允许自动收藏。保存进角色素材库的图片和表情在该角色的各聊天中都可直接查找和发送。 |
| 任务及发送记录 | 任务 ID、幂等键、操作、状态、结果素材或失败原因；发送另记目标聊天、消息回执、素材 ID 和时间。“重发原图”通过这条记录回溯。 |

文件先写临时位置，校验完成后按哈希原子归位，再用数据库事务登记。重复渠道事件以来源消息和附件序号识别。同一文件出现在不同群时只复用字节，同一角色在其他聊天也能使用已保存的原件。调整聊天偏好的图包会改变主动选图顺序。角色原创包按评估状态生效。

## Pi 工具契约

角色、账号与当前聊天由宿主注入。工具输出使用稳定 ID，消息引用必须属于本轮允许读取的范围。生图、收藏、检索、发送每次都按[通用工具权限](pi-runtime-integration-design.md)校验发起人身份、工具权限和操作目标。例如，用参考图生成新图要有权读取该素材，之后发送成图要有权发往目标聊天。付费生图通过授权后再检查次数额度。

| 工具 | 输入 | 成功结果 |
| --- | --- | --- |
| `generate_image` | 本次描述、用途（图片／表情）、可选参考素材、动作（新画／同题再画／编辑） | 任务 ID；完成后返回素材 ID 和预览，原创表情标为待评估，通过后加入角色原创包。 |
| `save_from_message` | 消息引用、附件序号、用途、可选别名 | 素材 ID、所在图包、原件或仅平台内复用状态。 |
| `search_assets` | 引用、别名、画面或表达意图，以及可选日期、类型 | 该角色素材库中与查询匹配的少量候选，含 ID、预览、含义和最近使用时间。 |
| `send_asset` | 当前对话中选定的素材或候选 ID | 发送记录及状态；成功后关联平台回执。 |

### 调用示例与结果约定（建议契约）

四个工具共用宿主提供的角色、账号、聊天、回复轮次和操作标识。Pi 传入业务参数，宿主为同一逻辑动作的重试复用操作标识。用户明确要求“再画一张”会创建新动作，即使文字完全相同。

| 工具 | 调用示例 | 结果与分支 |
| --- | --- | --- |
| `generate_image` | `{"action":"new","purpose":"sticker","prompt":"Q 版生气，鼓脸抱臂"}` | `action` 可取 `new / variation / edit`，`purpose` 可取 `image / sticker`。后两种动作必填 `sourceAssetId`。受理返回 `{status:"queued",jobId}`；任务完成由宿主按该 ID 发布一次结果，包含 `assetId`。 |
| `save_from_message` | `{"messageRef":"m42","attachmentIndex":0,"purpose":"sticker","alias":"假装在听"}` | 索引从 0 起算。只有一个附件时可以省略；多个附件且未选定返回 `needs_selection` 和当前消息可选项。成功结果注明 `local_original` 或 `platform_only`。 |
| `search_assets` | `{"purpose":"sticker","query":"尴尬，但想表示赞同"}` | 也可按 `messageRef` 定向查找，或用日期范围缩小文字查询。返回有序 `candidates`，无匹配返回空数组。明确要求找旧图且存在歧义时让用户选。 |
| `send_asset` | `{"candidateId":"c2"}` | `candidateId` 与 `assetId` 二选一。候选绑定本轮及素材。发送时检查素材仍在该角色库中且目标支持相应格式。素材已移除时返回 `asset_unavailable`。 |

**一次生成、一次发送。** 生图工具只负责生成入库。需要在聊天展示成图时，宿主把任务完成事件关联到原回复计划，由统一发送入口消费一次。原创表情先等评估通过，管理界面发起的“只保存”任务仅提示入库。重复完成通知不重新发图。渠道发送直接展示接口返回的成功或错误。

**提示组装与能力检查。** 每次保存角色外观引用、场景、画风、表情要求和发给后端的最终参数快照。初始角色卡的五个字段沿用[已确认决策](pi-refactor-decisions.md)；外观参考由素材模块按角色引用。没有参考图时，纯文字生图用当前可用的外观描述。用户明确要求保留指定原图时，若后端缺少编辑能力，在调用前返回 `unsupported_edit`，告知可以重画。归档时只记录后端实际提供的种子和模型版本。

### 任务所有权与重启恢复

| 中断位置 | 恢复动作 |
| --- | --- |
| 任务已入队，尚未开始外部调用 | worker 用事务领取。抢占失败的 worker 跳过；已确认无外部提交的任务可重新执行。 |
| 即将提交或已提交，连接中断／进程退出 | 调用前持久化操作键和提交中状态，能取得供应商任务号时立即保存。优先用操作键或任务号查询；只有能证明未提交或后端明确支持幂等重放时才重试，否则进入待核对。 |
| 原件已落盘，SQLite 尚未登记完成 | 恢复时按任务暂存记录与哈希校验已有文件，补齐素材和版本事务；重放同一任务只产生一个结果素材。 |
| 已入库，发送报错 | 保留成图，直接返回渠道错误。主人重新发送时使用同一素材。 |

素材保存前按当前聊天权限读取附件。入库之后，同一角色可在私聊和群聊中使用该图片或表情，用群内收藏的图作参考生成的表情也遵循这条规则。查看来源消息仍按原聊天权限处理。只有平台贴纸 ID 的条目按目标平台实际支持的方式发送。

## 核心行为

1. **生图和改图。** 固定外观、当次场景、画风和用途分别组装。普通成图进入图片库；“Q 版生气表情”使用同一后端，评估通过后加入角色全聊天可用的原创包。编辑引用原图时创建派生版本。后端只支持按文字重画时，先让用户选择是否重画。“把第一张再发我”只读发送记录并补发原件。
2. **手动和自动收藏。** 手动收藏以被引用消息为准；多附件且指代不清时展示缩略图供选。手动指定的别名立即可查。自动收藏建议默认关闭，启用后优先接收平台明确标识的表情。视觉标注异步补全画面内容和表达语气，主人命名优先。只有平台贴纸 ID 时记录可复用的账号与平台范围。
3. **主动选用。** 当前聊天开启主动发表情后，角色从已收藏的素材和已通过评估的原创表情中选取。按偏好图包、本群别名、主人标注、表达含义和画面内容排序，最近使用过的降权。建议首版使用 SQLite 标签及短词匹配。回复计划可选择文字、表情或文字配图，同一表达动作只发一次，发前核对目标聊天和当前话题。
4. **失败恢复。** 成图成功而发送失败时保留素材，重试发送复用同一文件。付费生图已提交但结果未知时，优先按生图后端任务号查询。无法确认时保留待核对状态。

### 自主付费请求与次数限制

角色可在配置的次数上限内自主提交付费生图。建议由宿主识别自主任务，按配置的额度范围和时间窗口在 SQLite 中原子预占一次，再提交供应商。所有聊天共用相应额度；工具重放复用原任务，超限返回 `quota_exhausted`，前端展示剩余次数和恢复时间。只有确认尚未提交时才释放预占；已提交、结果未知或成图被丢弃均保留计数。重发已有素材不占用生图次数，发起新的重画请求需要新的额度。

### 原创表情效果评估

每张原创表情的正常流程固定为两次请求：一次生图，一次视觉评估。评估同时接收成图、当次角色参考（如有）、已知外观特征和创作要求，可附上本地生成的聊天尺寸预览。生图与评估分别记账。Pi 对话和状态轮询单独统计。

评估先判两项。① 角色是否画对：对照参考图或明确的外观描述，核查发型、发色、标志配饰等可见特征，允许 Q 版简化。② 画面形式是否符合本次要求：要求 Q 版表情时，检查简化造型、比例以及缩小后是否能读出主要表情或动作；正常比例立绘即使人物和情绪正确也不能通过。评估应分别给出结论和可见依据。角色参考不足时进入待挑选；任一项明确失败即退出候选，不自动重画。两项通过后，在同一请求中判断情绪含义和小图可读性。

前端提供预览、原因和采用／丢弃操作。采用后该角色的全部聊天均可选用，实际主动发言仍遵守聊天设置。待评估或丢弃的条目从聊天候选及发送入口排除。丢弃后已缓存的候选即时失效，其他素材对同一原件的引用继续有效。

样图验收至少覆盖三种组合：角色正确但画成普通立绘、画成 Q 版但角色错误、角色和 Q 版形式均正确。前两张应分别报告对应原因，第三张再按表意验收。一次生成搭配一次评估即可区分三种情况。

## 界面与验收

图片库按日期、来源聊天、角色参考与版本查找；表情库按图包查看静图和动图。聊天消息提供“收藏为图片／表情”，输入框提供素材选择器。素材详情展示原始来源、派生版本、包内含义、使用范围及最近使用记录。

| 开发验收场景 | 应观察到的结果 |
| --- | --- |
| 仅启动开发前端和已配置生图服务，在前端输入提示词并生成 | 能看到任务状态、真实结果和预览；失败有可读原因。生图可用性可独立于渠道发送验收。 |
| 自主付费额度剩 1 次，两个聊天同时请求生图 | 最多 1 个新请求提交供应商，其余提示超限；重启后计数一致。 |
| 原创表情生成并完成评估，随后又被丢弃 | 通过后同一角色在两个未绑定收藏包的聊天均可选用；丢弃后两个聊天都搜不到，旧候选也无法发送，不自动退还或消耗额外次数。 |
| 同一角色先画立绘，再要求“画个 Q 版生气表情” | 两次均调用同一生图工具；后者带表情要求，通过效果评估后进入原创包，前者在图片库可查。 |
| 在 QQ 群收藏一张 GIF，换到私聊请同一角色发这张表情 | 按收藏时起的名字能找到并发出原动图。 |
| 用群里已收藏的图片作参考，请角色画一张原创表情 | 评估通过后，在另一个聊天里也能选用这张表情。 |
| 引用第一张图改出第二版，再要求重发第一版 | 版本关系可回溯，重发的原件哈希与第一版一致，生图调用次数不增加。 |
| 在某个群关掉主动发表情，再请角色发一张已收藏的图 | 角色不会自行配表情，明确点图时仍能发送。 |
| 生图成功、渠道发送失败后重试 | 图库保留成图，重试只触发渠道发送；付费提交结果未知时不会自动重复生成。 |

## 给开发模型的实施顺序

1. **先交付“收得回、找得到”。** 用隔离目录、临时 SQLite 和测试渠道，走通引用收藏 GIF、重启、按群内别名找回和手动重发。观察原件哈希、动画帧数、目标聊天与回执。
2. **再交付“会画、会改”。** 用可计数的假生图后端覆盖新画、表情、改图、超时；复用同一生成入口。在生成后、发送前模拟退出并重启，断言生成提交次数、素材数、发送记录数。假后端负责验证编排；画面是否像同一角色需要另做真实样图评估。
3. **最后交付“会自己用”。** 把收藏开关、图包选择、预览和发送接到正常聊天入口。在私聊与群聊中查找同一张收藏图，核对主动发表情开关、偏好图包和实际发出的图片。
4. **对接真实服务前核实依赖。** 从新版实际工作区确认 Pi 版本、扩展注册及任务完成通知入口，记录目标渠道可下载／可发送的媒体类型和回执能力，核实首个生图后端的改图、查询、幂等能力。执行命令以该工作区的清单和脚本为准。报告分别列出通过的自动化用例、真实联调范围和仍未验证的能力。

## 尚待确定的配置细节

- 自主请求的次数上限、计数周期和额度范围（如按角色或整个实例），以及主人手动生图是否共用额度。开发测试使用显式的小额度，不据此设定产品默认值。
- 生图后端选择以能在前端实际使用为准，渠道联调单独验收。自动评估采用的模型、通过标准和样图集仍待验证。
