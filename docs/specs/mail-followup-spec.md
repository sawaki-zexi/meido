## 用户结果

主人可以看到线程当前是“仍待主人处理”“等待对方回复”还是“已关闭”，并可开启到期提醒和默认关闭的到期自动催复草稿。提醒通过现有指定角色投递；催复草稿写入 QQ 草稿箱但不会自动发送，也不把提醒当作待办事项。

## 状态来源

- `to_reply`：线程最新事件是主人尚未完成处理的来信，或主人仍有未完成的承诺。
- `awaiting_reply`：主人最新邮件明确向对方提问、请求回复/反馈，或等待对方兑现承诺；主人单纯发送信息不自动进入此状态。
- `closed`：最新来信已明确判断为无需回复，或主人手动关闭当前线程跟进。
- `unknown`：事件方向或数据不足以安全判断。

状态基于本地 inbound/outbound 邮件事件和发送副本关联，不仅按发件人字符串翻转。主人手动覆盖绑定当前事件指纹；新来信或新发送事件到达后旧覆盖自动失效。

## 线程分析契约

每次线程刷新同时保存一份可解释的分析对象。当前实现使用 `signals-v3`，先清理明确的引用正文，再按事件方向、处理状态和中英文问题、承诺、结束信号提取候选事项；引用段、否定承诺和仅包含日期的请求不会直接作为承诺。承诺可包含显式日期、相对日期或星期的 `dueAt`；后续同一责任方明确完成时保留原证据，并设置 `status=fulfilled` 和 `fulfilledByEventId`。主人发送信息、报告或建议但没有明确请求回复时按已处理关闭，只有明确问题/请求才进入等待对方状态。`nextDueAt` 取尚未兑现承诺的最近截止时间。分析失败或事件为空时返回 `unknown` 和 `verify_thread`，不把不确定性压缩为 `closed`。

分析对象包含：

- `nextAction`：`none`、`review_or_reply`、`owner_complete_commitment`、`wait_counterparty`、`wait_counterparty_commitment` 或 `verify_thread`。
- `openQuestions`：问题事件的 `eventId`、`itemId`、责任方、事项类型、当前状态、摘要和时间。
- `commitments`：承诺事件的同样证据字段；承诺优先于同一邮件中的结束语。
- `evidenceEventIds`：解释当前状态的事件 ID，保持稳定顺序。
- `classifier`：分类器版本，便于后续比较规则版和模型版。
- `dueAt`、`fulfilledByEventId`：承诺截止时间与后续兑现邮件的引用；明确时刻保留原文时区后转换为 UTC，只有日期时按来源邮件时区的当天结束处理；无法从邮件明确解析日期或星期时不推测截止时间。
- `nextDueAt`：当前未兑现承诺中的最近截止时间，供行动列表和提醒调度使用。

分析中的摘要只用于当前账号的邮件详情和已授权的 `mail.manage` 查询；普通角色消息、长期记忆和日志不保存邮件全文，`mail.manage` 的完整工具结果只在当前运行内存中可见，持久会话仅保留脱敏标记。线程状态、提醒和准备结果同时绑定账号连接代次；同账号重连或账号切换后旧快照显示为 `unknown/verify_thread`，必须重新同步核实。人工关闭仍只覆盖当前事件指纹，新事件到达后恢复自动判断。

## 行动列表

`GET /api/mail/threads` 返回当前账号每个本地线程一行，支持 `state`、`action`、`query`、`limit` 和 `offset`。`action` 除具体下一步外还支持 `needs_input`（存在待主人补充的持久准备结果）、`overdue`（未兑现承诺的截止时间已到）和 `needs_verification`（线程状态未知或存在未核实远端写入）。线程尚未生成持久跟进状态时，接口按当前本地事件即时分类；此只读查询不触发 IMAP 同步、提醒投递或邮件写入。查询和线程详情共享同一账号范围，关键词搜索覆盖线程中的主题、发件人、收件人和正文。行项目提供最新邮件 ID、状态、下一步动作、截止/提醒时间、问题/承诺数量、草稿数、待补充、到期和待核实标志。`unknown` 固定显示 `verify_thread`，`closed` 固定显示 `none`；人工状态覆盖时，下一步动作与覆盖状态一致。

邮件详情同时返回 `threadDossier`：整条线程的邮件 ID、所有草稿版本、各封邮件的准备结果和未核实写入。用户从线程行动进入任一最新邮件时，仍可定位每个事项、草稿版本及其来源，不需要逐封切换才能判断线程下一步。

## 提醒

提醒默认关闭。开启后，`to_reply` 和 `awaiting_reply` 按主人设置的小时数计算到期时间；线程事件指纹、状态和提醒调度 generation 组成唯一 `due_key`，同一事件在同一调度代次最多投递一次。主人修改提醒间隔、关闭后重新开启或其他提醒设置变化时，旧的 pending/failed 调度先取消，再以新的 generation 计算新的到期时间；历史账本保留。投递前提醒批次和线程提醒都要以事务原子认领为 `sending`，并发调度只能由一个执行者投递；服务重启时中断的 `sending` 恢复为 `failed`，可由后续同步重试。投递失败保留失败次数和错误，可由后续同步重试；线程状态变化或提醒被关闭时，旧提醒取消。

开启“到期自动生成催复草稿”后，仅对已确认 `awaiting_reply` 的线程在提醒到期时执行一次催复准备。自动动作使用与线程事件绑定的稳定任务键和 QQ 草稿 marker；同一线程事件无论重启、重复同步或提醒投递失败，都不会重复调用远端 APPEND。生成成功后仍通过提醒角色告知主人，最终审核和发送仍由主人在 QQ 完成。模型返回 `needs_input`、准备失败或远端写入不确定时，任务保留可诊断状态并可重试/对账。

## 边界

- 提醒角色必须是主人已指定且当前可用的角色。
- 不自动发送、删除、归档或移动邮件。主人可以在详情页明确请求为 `awaiting_reply` 线程生成一封催复草稿，也可以显式开启到期自动生成；自动开关默认关闭。
- 催复草稿只在最新事件仍是主人实际发送的邮件、对方收件人可由该事件明确解析且线程指纹未变化时生成。写入使用稳定的线程事件任务键，重复请求不会追加第二封；模型返回 `no_reply` 或 `needs_input` 时不写入 QQ 草稿箱。
- 催复草稿沿用普通草稿的来源记录、版本、账号代次、人工修改保护、APPEND 回读和未知结果对账；不因远端状态不明删除或覆盖旧草稿。
- 线程提醒与草稿/待补问题提醒分开保存，互不覆盖。
- 发送副本关联不唯一、Sent 读取失败或账号代次变化时，线程进入待核实路径，不生成确定性跟进结论；Sent 读取失败会将现有 `to_reply`/`awaiting_reply` 状态转为 `unknown`，取消未投递提醒，待下一次成功同步后重新判断。

## 验收

- 同一线程重复同步不会重复创建或投递提醒。
- 发送副本匹配后线程从 `to_reply` 转为 `awaiting_reply`；新来信后回到 `to_reply`。
- 主人关闭线程后重复同步仍保持关闭；新事件到达后自动恢复判断。
- 关闭提醒不会删除历史账本；未投递提醒变为取消状态。
- 修改提醒间隔或关闭后重新开启会取消旧调度，并创建带新 generation 的新调度；旧调度不会再次投递。
- Sent 读取失败时线程显示 `unknown`，不会产生新的提醒；恢复读取后才重新计算方向和到期时间。
- 角色不可用或投递失败不会丢失提醒，界面能看到失败状态。
- 行动列表在持久刷新前也包含当前账号线程；状态、动作、关键词和分页筛选一致，手动关闭与 `unknown` 不显示过期动作。
- 行动列表可以按待补充、已到期和需核实筛选；线程详情聚合该线程的草稿、准备结果和未核实写入。
- 对方承诺“明天交付”时保存可定位的截止时间；同一方后续明确确认完成后原承诺标记兑现，不再驱动待办或提醒。
- 开启自动催复后，到期的 `awaiting_reply` 线程最多创建一个可审核 QQ 草稿；关闭开关、线程出现新事件或线程状态改变时不创建陈旧草稿。
- 自动催复在 QQ 写入结果不确定时只保留原 marker 对账状态，不重复追加；角色提醒不可用不会导致草稿被删除或覆盖。
