# Meido 第一版 MVP 技术方案

状态：草案

本文记录第一版 MVP 已确认的技术方案，以及开发前仍需确认的实现选项。未确认的实现方式不应被视为产品决定。

## 1. 范围

第一版只实现以下闭环：

```text
创建角色
  -> 打开角色唯一会话
  -> 与角色进行流式对话
  -> 修改角色设定并继续对话
  -> 删除角色及其唯一会话
```

第一版不包含：

- 长期记忆、向量检索和记忆维护
- `SELF.md` 或人格自动成长
- 多会话、会话分支和会话摘要
- 邮件、浏览器、任务、工具和技能
- 定时任务、主动消息和多平台接入
- 角色素材库和角色级模型选择
- 角色导入、导出、版本回滚和回收站

## 2. 已确认的架构决定

### 2.1 部署形态

采用本地前后端结构：

```text
浏览器网页前端
  -> 本地后端服务
  -> 本地角色、会话和消息存储
  -> 模型服务
```

第一版不做 Electron 或 Tauri 封装。桌面应用可以在后续复用同一套后端和网页前端。

### 2.2 角色与会话关系

- 每个角色拥有不可变且唯一的内部 ID。
- 角色名称不是身份标识，可以重复。
- 一个角色只对应一个持续会话。
- 角色改名不会改变角色 ID，也不会创建新会话。
- 会话的逻辑标识可以采用 Shiori 风格的 `role:{role_id}`。

### 2.3 角色资料结构

角色设定的组织方式参考 Shiori 的角色资料结构，但不复制其完整功能。第一版角色至少包含：

- `name`：角色名称，必填且不能只包含空格
- `description`：角色简介，可选
- `profile`：身份、背景和基本设定，必填且不能只包含空格
- `personality`：性格，可选
- `behavior_rules`：行为规则，可选
- `response_constraints`：回复限制，可选
- `nickname`：称呼或昵称，可选

### 2.4 流式对话

女仆回复采用流式生成和逐步显示。逻辑事件至少包括：

```text
user_message_accepted
assistant_generation_started
assistant_delta
assistant_completed
assistant_failed
```

具体使用 SSE、WebSocket 或其他本地流式传输方式尚未确定；传输实现必须能够表达以上状态，并支持错误和断开处理。

### 2.5 角色级串行生成

同一角色同一时间只允许一个生成中的回合。这样可以保持唯一会话中的消息顺序和上下文一致性。

角色设定修改不影响已经开始生成的回复。每次生成开始时读取并固定角色设定快照；修改只影响后续回合。

## 3. 领域模型

### 3.1 Role

角色是持久化的身份和设定对象。建议包含：

- `id`
- `name`
- `description`
- `profile`
- `personality`
- `behavior_rules`
- `response_constraints`
- `nickname`
- `created_at`
- `updated_at`

角色设定字段由后端校验和保存，前端只负责编辑和展示。

### 3.2 Session

会话是角色唯一的持续聊天容器。建议包含：

- `id` 或由 `role_id` 派生的稳定键
- `role_id`
- `created_at`
- `updated_at`

后端必须保证同一 `role_id` 不会创建第二个会话。

### 3.3 Message

消息至少包含：

- 唯一 ID
- `session_id`
- 消息身份：`user` 或 `assistant`
- 文本内容
- 发送时间
- 生成状态（女仆消息需要区分完成、失败或未完成）
- 稳定的显示顺序

用户消息和完整的女仆回复才作为正常完成消息保存。流式生成中断时，未完成内容不得被标记为完整女仆回复；可以保留失败记录用于界面提示和诊断。

## 4. 对话上下文

每次模型调用使用：

```text
角色设定快照
  + 当前会话的历史消息窗口
  + 当前用户消息
```

角色字段以固定顺序编译为模型上下文，至少区分角色身份、性格、行为规则和回复限制。具体 Prompt 文本参考 Shiori 的角色 Prompt 编译思路。

第一版：

- 保存完整会话历史
- 只向模型发送符合上下文预算的最近消息
- 按完整对话回合截断
- 不做长期记忆、摘要或向量召回

## 5. 角色生命周期

### 创建

1. 用户打开本地网页的角色列表。
2. 填写角色字段。
3. 后端校验名称和角色设定。
4. 后端生成不可变角色 ID。
5. 后端保存角色并建立唯一会话。
6. 前端进入角色详情或聊天页面。

### 编辑

1. 用户进入角色维护页面。
2. 前端加载当前角色设定。
3. 用户编辑并可取消未保存修改。
4. 后端保存成功后更新角色设定和更新时间。
5. 后续生成使用新设定；正在生成的回合继续使用开始时的快照。

### 删除

1. 用户从角色维护页面发起删除。
2. 前端明确显示角色名称和永久删除提示。
3. 用户确认后由后端执行删除。
4. 角色、唯一会话和消息一起删除。
5. 删除失败时保留原数据并返回明确错误。

## 6. 流式失败和恢复规则

- 空消息不能发送。
- 模型请求失败时，前端显示明确错误，用户可以继续发送。
- 流式回复中断时，回复状态为失败或未完成，不作为完整女仆消息保存。
- 用户消息不得因女仆回复失败而丢失。
- 页面刷新后，已完成消息顺序保持不变。
- 第一版不做流式回复断点续传。

## 7. 模块边界

### 网页前端

负责：

- 角色列表、创建、详情、编辑和删除交互
- 唯一会话页面和消息展示
- 流式增量展示、生成状态和错误提示
- 本地后端连接状态

不负责：

- 角色 ID 生成
- 角色字段最终校验
- 会话唯一性保证
- 消息最终持久化
- 模型调用

### 本地后端

负责：

- 角色 CRUD
- 角色与唯一会话的绑定
- 消息持久化和历史窗口读取
- Prompt 编译和角色快照
- 模型调用和流式事件转发
- 角色级并发控制
- 删除时的数据一致性

### 模型适配层

第一版只需要一个默认模型配置，但后端应通过内部适配边界调用模型，避免领域逻辑直接依赖某个供应商 SDK。暂不支持按角色选择模型。

## 8. 持久化原则

持久化设计参考 Shiori 的分层职责：角色定义、会话状态和消息历史分别由所属服务管理，业务模块不能通过前端状态直接作为权威数据。

具体采用 JSON、SQLite 或其他本地存储实现尚未在本 Spec 中拍板；无论采用何种实现，都必须满足：

- 角色 ID 稳定
- 角色和会话关系唯一
- 消息追加顺序稳定
- 删除角色时不会留下可访问的孤立消息
- 页面刷新后可恢复角色和会话

## 9. 尚未解决的技术问题

以下问题需要在开始编码前单独确认，不应由 Issue 验收标准隐式决定：

1. 前端具体技术栈和开发服务器。
2. 本地后端具体语言和 Web 框架。
3. 流式传输采用 SSE、WebSocket 还是其他方案。
4. 角色、会话和消息的具体存储引擎。
5. 默认模型供应商、模型名称和 API Key 配置方式。
6. 本地后端的启动、停止和端口配置方式。
7. 是否需要本地服务访问控制，以及是否只绑定回环地址。

## 10. MVP 验收场景

### 场景一：创建并恢复角色

创建一个角色，刷新网页，角色字段保持不变；角色名称可以重复，但每个角色仍能被内部 ID 正确区分。

### 场景二：持续唯一会话

进入角色并发送多条消息，刷新网页后消息顺序和角色会话保持不变；同一角色不会出现第二个独立聊天。

### 场景三：流式回复失败

模型生成过程中断，界面显示失败或未完成状态；用户可以继续发送消息，失败内容不被当作完整女仆回复。

### 场景四：修改设定

修改角色设定后发送新消息，新回复使用新设定；修改期间已经开始的回复不被改变，历史消息保持不变。

### 场景五：删除角色

确认删除角色后，角色、唯一会话和消息都无法继续访问；取消确认或删除失败时，原数据保持不变。
