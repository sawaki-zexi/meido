## 1. 目标与范围

主人可以把角色账号连接到 Telegram、QQ NapCat、官方 QQBot 和飞书，从手机渠道私聊或在受支持的群聊中与角色交互；Meido 网页能查看这些渠道会话，并随消息实时更新。角色回复、身份识别、群触发、工具权限、主动发送和消息历史都由 Meido 宿主统一处理，平台适配器只负责连接、事件解析和平台 API。

本功能复刻 Shiori 的账号归属、一次性配对、私聊/群聊线程隔离、主人识别、外部工具限制、群旁听、群记忆工具、账号目标发现、主动发送、发送回执和网页会话同步。首期不引入云端服务、多主人账户、动态插件市场或远程插件执行环境。

## 2. 已确认的产品行为

- 未配对用户可以向已启用的角色渠道账号私聊；账号可独立关闭私聊/群聊，并可按发送者 ID 或平台别名屏蔽用户。
- 支持的平台能力按下表执行。能力不可用时必须在 UI、配置诊断和目标目录中明确呈现，不得伪装成统一能力。
- 群聊只有在 @ 角色或回复角色消息时触发回合；群旁听是按群独立启用的选项，不触发 Agent 回合。
- 已配对主人在群里触发回合时可使用与 Shiori 相同的主人级工具；该回合仍只读取当前群原文。其他群、陌生私聊和桌面历史不能因主人身份而自动并入群上下文。
- 陌生人回合只能使用显式标记为 `external_allowed` 的工具；模型声明工具和服务端执行工具都必须检查权限。非主人不能让角色向任意第三方投递消息。
- 网页提供渠道会话列表和分页历史，并实时收到外部入站、角色回复、主动投递及旁听更新。通过 QQ、Telegram、飞书发送的消息仍从相应渠道产生；网页查看/同步不创建另一份聊天。
- `account_targets` 只返回账号实际可达或已观察到的目标；`account_send` 只能选择目录项，且平台不支持的目标类型必须拒绝。
- 完整实现渠道回复和主动发送状态，区分 `pending`、`sent`、确定失败和结果不确定；不确定的发送不得自动盲目重发。

## 3. 平台能力矩阵

| 适配器 | 私聊 | 群聊 | 群触发 | 旁听 | 目标发送 |
| --- | --- | --- | --- | --- | --- |
| Telegram Bot | 支持 | 支持 | @角色或回复角色消息 | 按 Shiori 当前基线不提供 | 已观察到的私聊/群聊；能力由 Bot 权限决定 |
| QQ NapCat / OneBot | 支持 | 支持 | @角色或回复角色消息 | 支持，按群配置 | 已观察到的私聊、群和可发现群成员 |
| 官方 QQBot | C2C 私聊 | 首期不承诺 | 不适用 | 不支持 | 已观察到的 C2C 私聊 |
| 飞书 Bot | 支持 | 首期不承诺 | 不适用 | 不支持 | 已观察到的私聊 |

Telegram 群回复触发是建议优于 Shiori 当前基线的修正：Shiori Telegram 当前只把 @ 上报为触发条件，而 Meido 按已确认的 @/回复规则同时接受二者。Telegram Bot 隐私模式或平台权限不允许读取群消息时，UI 必须说明实际限制。

适配器分别声明私聊、群聊、旁听、媒体、回复、流式编辑和目标类型能力。Feishu 与官方 QQBot 的群聊支持只有在平台事件和权限完成实测后才能扩展，不以该规格中的“首期不承诺”阻塞其他渠道。

## 4. 账号与身份

每个角色每个适配器最多绑定一个账号，因此同一角色可各绑定一个 Telegram、NapCat QQ、QQBot 和飞书账号。账号记录归属角色、适配器、平台账号身份、启停/连接状态、私聊/群聊开关、屏蔽列表和显示信息。添加账号、验证连接、查看连接错误、修改响应规则及移除账号均可在网页完成。账号移除停止后续收发和凭据使用，不删除已经保存的会话历史。

Bot token、App secret 等凭据不得写入普通配置数据库、日志或诊断事件；所有渠道凭据共用 Meido 的系统凭据库接口。没有可用系统凭据库时，保存操作明确失败，不回退到明文存储。

主人使用桌面端生成一次性配对码。配对码 10 分钟有效、成功后立即失效，只能在私聊中使用；配对命令本身不进入角色历史、不触发角色回合。Telegram 和 NapCat QQ 的身份按平台作用域识别；飞书和 QQBot 的用户 ID 按应用账号作用域识别。解绑账号或身份后，后续消息重新按陌生人上下文处理。

配对从成功时刻起授权该私聊进入主人上下文，不能把配对前的陌生人历史追溯提升为主人历史。主人后续在新的私聊中发言时更新该账号的主动投递目标，并保留每个私聊各自的上下文起始边界。

## 5. 会话、线程和权限上下文

会话至少包含 `role_id`、稳定 `thread_id`、渠道、账号、平台 `chat_id`、私聊/群聊类型、群/联系人显示信息和最后活动时间。桌面聊天是独立 `desktop` 线程；每个渠道私聊或群聊都有独立线程。联系人名、群名、头像和 `ViaAccount` 来源快照用于展示，不作为授权依据。

每轮由可信宿主构造不可变上下文视图，并在构建模型消息、注入记忆、声明工具和执行工具四处复用：

| 回合来源 | 可读原始消息 | 身份权限 |
| --- | --- | --- |
| 桌面 | 桌面线程和已配对主人私聊的授权片段 | 主人级 |
| 已配对主人私聊 | 当前私聊配对时间之后的消息、桌面线程和其他已授权主人私聊 | 主人级 |
| 未配对私聊 | 当前私聊线程 | `external_allowed` |
| 群聊主人触发 | 当前群线程；群内按身份确认的主人消息标记为主人来源 | 主人级工具；群原文仍限当前群 |
| 群聊非主人触发 | 当前群线程 | `external_allowed` |
| 旁听 | 当前群的旁听记录，不创建模型回合 | 不适用 |

群聊天是否是主人上下文由发送者身份决定，不由群是否包含主人、是否绑定或插件提供的字段决定。插件上报的身份声明不可信；`sender_is_user` 和配对关系由宿主根据已存身份绑定重新计算。

主人资料、角色对主人的私有理解、主人关系记忆和桌面历史不得进入陌生人上下文。配对前消息不得因身份重算进入主人上下文。外部用户产生的个人信息按用户/线程隔离；群内容和群成员信息按群隔离。当前 Meido 已有的历史角色记忆迁移时按主人私有内容处理，避免首次接入后被陌生人检索。

## 6. 群聊、旁听与群上下文工具

群触发只由结构化 @ 或 reply 元数据判定，不依赖正文关键词。消息引用、@ 成员、发送者身份、群名和平台消息 ID 作为结构化字段保存。群回复遵循平台原生约定：回复触发消息，并在平台支持时提及触发者；平台不支持的可选提及不能阻断普通回复。

旁听只在 NapCat QQ 等声明该能力的适配器中开放，按角色/账号/群持久化开关。旁听内容独立存储、只属于该群，不回复、不触发 Agent、不被其他群读取；页面提供暂停和清理入口。旁听批次、保留时间和每日写入上限必须可诊断，不应静默丢弃后仍显示为已保存。

群成员档案、群环境和群笔记工具遵循 Shiori 的工具边界：陌生成员最多使用被明确允许的当前群只读能力；主人可在当前群管理该群旁听和上下文；跨群查询不能返回其他群原始聊天内容。群资料不能写入主人私有记忆或桌面 transcript。

## 7. 工具、目标目录与主动发送

每个 Tool 有机器可读的风险、可见性和授权策略。`external_allowed` 同时控制模型收到的 schema 和执行入口。所有外部回合中的 `account_send` 强制目标为已配对主人；模型不能通过伪造账户 ID、原始 chat ID、群成员 ID、mention ID 或工具参数绕过目标选择。

`account_targets` 按当前角色账号返回平台实际可达或运行中观察到的私聊、群和可获取的群成员，返回稳定的目录项 ID、类型、显示名和可用能力。目录项经平台能力校验后才可用于 `account_send`。模型只传目录项 ID，不传任意平台目标 ID。用户/主人目标由宿主从配对身份解析，不能伪造成插件目标。

角色回复和主动投递都必须写入与目标线程关联的消息记录，网页显示实际来源账号快照和平台回执。投递账本保留目标、调用来源、尝试时间、状态、平台消息 ID 和安全错误摘要。仅平台明确拒绝才标记确定失败；超时发生在请求可能已被平台接受时标记 `uncertain`。重启恢复时保留不确定状态并提供人工检查，不自动重复发送。

图片、文件和引用消息沿用 Shiori 的结构化消息/媒体能力。入站下载需有文件大小、MIME、超时和本地保存边界；附件路径不得跨线程授权。平台不支持的附件、引用或群目标必须返回明确错误并保留可发送的其他内容。

## 8. 网页同步

按角色列出网络线程，按最近活动倒序显示渠道、账号、联系人/群、线程类型、最近消息和未读/活动状态。进入线程后按稳定顺序分页读取消息；列表和聊天面板适配手机与桌面宽度。账号删除后历史保留，来源账号可显示为已移除。

收到外部消息、角色回复、主动消息或旁听事件后，网页通过现有实时事件通道更新列表和当前线程，不需要整页刷新。历史分页、当前选中线程、引用、@ 和媒体加载不因其他线程有新消息而跳动。网页端只表示“查看渠道会话”，发送按钮按产品定义不冒充渠道发送；实际渠道发言经已接入的外部应用进行。

## 9. 架构建议与相对 Shiori 的改进

建议复用现有 `role:<role_id>` Runtime/session 作为角色级生命周期和并发边界，但将 thread、account、sender 和身份信任建成显式结构化字段，而不是只写入可选 JSON metadata。唯一 `ConversationContextBuilder` 负责产生受限消息集合和 Tool 权限；持久层查询必须要求明确的线程/授权线程集合。这样保留 Shiori 的共享角色运行语义，同时让线程过滤可以由 SQL 查询和测试直接验证。

建议记忆增加明确可过滤的可见性/来源分类：旧桌面记忆默认为主人私有；陌生人和群回合的记忆只落在对应身份或群作用域；主人资料仅对主人上下文可见。不可见记录必须在检索前排除，而不是依赖 prompt 要求模型不引用。

Shiori 的主人群回合可以使用全部主人工具，本次按已确认行为完整保留。高风险工具执行后可能把私有信息或外部副作用带入多人群聊；按群限制主人级 Tool 是后续安全增强建议，不属于本次 Shiori parity。

Shiori Telegram 当前只用 @ 触发群聊；本规格建议接受 @ 和回复，匹配已经确认的触发规则。Shiori 的 pending 发送尝试在未知平台回执时可能长期不明确；本规格补充独立 `uncertain` 状态和人工核对，避免把“结果未知”当作“发送失败”后重复外发。

Shiori 当前用单个进程内全局队列逐条处理所有角色的入站消息；慢回合会阻塞其他角色，重启会丢失尚未处理的消息。Meido 的 Runtime 当前在同角色运行冲突时拒绝新运行。持久化并行入站队列不是 Shiori 基线，暂不列入验收；若后续采用，建议按角色串行、跨角色并行，持久保存已接收事件、重启恢复，并在执行时重新校验群触发和权限。该增强可减少跨角色阻塞和重启丢失，但会增加入站状态、恢复与队列满策略。

PR #115 增加的 `SystemCredentialStore` 当前使用 `meido.owner-knowledge` 固定凭据服务名。渠道凭据应复用同一系统凭据库能力，但扩展为具命名空间的 service/key（例如按插件与账号区分），并保留旧主人资料键兼容；不能让多个账号覆盖同一凭据键。

## 10. 数据迁移与失败恢复

现有 `role:<role_id>` 历史全部归入 `desktop` 线程，消息 ID、顺序、工具结果和运行记录保持可读；不拆分或丢弃既有对话。新增渠道数据迁移可重复执行，角色删除按角色清理渠道账号、身份、线程、附件、旁听、成员档案和投递记录；账号删除保留消息来源快照及历史。

外部消息先按平台事件 ID 短期去重，再以线程和外部消息 ID 持久去重。回合/消息提交、运行记录和手机更新事件遵循已有 Runtime 提交语义。连接配置换代应先启动并验证新传输，再停旧连接；已接受的发送固定到原账号代次。服务重启后未完成模型回合按当前 Runtime 恢复规则收束，投递状态依回执记录保留。

## 11. 验收标准

- 主人可以在网页添加、测试、停用、修改和移除四种适配器账号，凭据不出现在普通数据库、API 响应、日志或诊断中。
- 配对码单次有效、过期拒绝、仅私聊接受；成功配对的消息不会触发模型，配对前的陌生人消息不提升权限。
- 陌生人私聊收到角色回复，不能读到桌面、主人资料、主人记忆、其他私聊、其他群或任意第三方目标。
- 每个群/私聊有独立线程；在一个外部线程中不出现其他外部线程的原文。回归测试覆盖误传 thread ID、伪造身份 metadata 和错角色账号。
- 支持群聊的适配器仅在 @ 或回复时生成回合；旁听只写当前群记录，不回复或触发工具，且仅能力矩阵声明旁听的适配器开放开关。
- 主人在群中触发时可使用 Shiori 主人级工具，且原始聊天上下文限当前群；只有被绑定身份的消息可授予主人工具权限。
- `account_targets` 不返回未观察/不可达目标；`account_send` 拒绝目录外 ID、未支持类型和外部回合跨目标发送。
- 平台确认、明确拒绝、请求不确定三种投递结果分别可观察；重启后不确定发送不会自动重复。
- 网页支持网络线程列表、分页消息、媒体/引用/来源展示，并在外部新消息和回复后实时更新。
- 数据迁移后现有桌面消息和运行可见；重复迁移不重复创建线程；删除角色按范围清理且不影响其他角色。
- 四个平台适配器有接口契约测试；权限/上下文有矩阵测试；重启、去重、配置换代、附件边界和 Web 实时同步有集成测试。

## 13. Shiori 之外的改进建议

1. 主人群聊权限继续按 Shiori 开放全部主人级工具。若后续增加每群高风险 Tool allowlist/denylist，应作为独立权限决策，不改变本次验收。
2. Shiori 使用全局内存队列；按角色持久队列可以避免跨角色阻塞和重启丢失，但不属于本次复刻范围。
3. 飞书和官方 QQBot 首期按 Shiori 只支持私聊；扩展到群聊前需先实测平台事件和权限。
