## 1. 目标与范围

Meido 为单一主人提供 QQ 邮箱的本地处理入口：连接并验证邮箱、同步收件箱、判断是否需要回复、在 QQ 草稿箱创建回复草稿，并在网页或角色对话中查看和管理处理状态。最终审核和发送仍由主人在 QQ 邮箱完成。

本规格覆盖 Issues #92–#98。当前只支持 QQ 的 SSL IMAP 连接（993 端口），不解析附件，不使用 SMTP，不提供发送、删除、归档或移动邮件的入口。

## 2. 连接与凭据

主人在网页填写 QQ 地址和授权码后，后端把待测凭据保存到系统凭据库，测试和保存生效连接分为独立步骤。连接测试发现并读取收件箱、已发送和草稿箱，按 IMAP 文件夹标志优先、名称兼容规则兜底；空文件夹是有效状态。

只有以下流程全部通过，连接才进入可自动起草状态：

1. SSL IMAP 登录和三个文件夹访问成功。
2. 主人明确发起测试草稿写入，且后端从 QQ 草稿箱再次读到测试标记。
3. 主人在 QQ 网页端编辑并手动发送测试草稿，后端在已发送文件夹核验到同一标记。

认证信息只由本地后端读取，不进入 HTTP 响应、模型上下文、角色消息或普通日志。测试失败不能替换已有可用连接。

## 3. 同步与邮件模型

同步按邮箱账号和文件夹隔离 UID checkpoint，来源键为账号作用域加 `文件夹/UID`；切换账号不会合并邮件或复用其他账号的同步进度。重复同步、重启恢复和手动同步共享同一套去重规则；读取使用 `BODY.PEEK`，不修改原邮件已读状态。每封邮件保存发送者、Reply-To、收件人、主题、接收时间、Message-ID、线程关系、正文和处理状态。新邮件归入已有线程时，关联草稿会标记为可能过时；已人工修改的草稿保留人工修改标记并同时置过时标志。

自动轮询只在服务启用、未暂停且连接已验证时运行。暂停保留已有数据和任务结果；恢复或重启后从上次成功 checkpoint 继续。网络、认证或写入核验失败保留错误或待核实状态，不伪装成无新邮件。

## 4. 判断与草稿

自动处理在独立邮件任务上下文中运行。模型输入可以包含当前邮件、同线程邮件、主人资料检索结果和已发送邮件样本；不得包含邮箱凭据。模型只返回 `needsReply` 和正文：无需回复时不写草稿，需要回复时写入带原始 Message-ID 和 References 的 QQ 回复草稿。

草稿写入后立即从 QQ 草稿箱按 Meido 标记重新读取并核验。核验不到时状态为“待核实”，可以在后续同步或安全重试中恢复；不把不确定结果记为成功，也不发送邮件。

同一来源邮件的自动处理任务使用稳定幂等键，重试和服务重启不会重复创建自动草稿。主人手动创建的草稿和角色操作同样写入本地映射和审计记录。

任务队列、处理任务和草稿查询都绑定当前 QQ 账号；切换账号后，旧账号的邮件、线程、草稿和未完成任务不会出现在新账号的网页或角色入口中。已有单账号数据库会在启动时把旧记录迁移到保存的账号作用域。

## 5. 人工修改与版本

每个草稿保存最近一次 QQ 端内容哈希。后续同步发现 QQ 端内容变化时标记为 `manual_modified`/`stale`，删除时标记为 `missing`。普通自动处理、失败重试和新来信不会静默覆盖人工修改的草稿。

主人明确选择“创建新草稿版本”时，系统先核对 QQ 端当前草稿，再以新的任务键和标记追加一个新草稿；原草稿及其人工修改状态保留。网页详情必须展示同一来源邮件的全部草稿版本及各自状态。

## 6. 入口与提醒

网页提供连接、启停、同步、邮件分页列表/完整线程/多版本草稿详情、单封处理、线程处理、全部待处理任务、重试和创建新版本入口，但不提供发送按钮。网页派发任务返回受理标识，后台持久任务队列公开排队、运行和终态；服务重启后恢复未完成任务，网页可继续查询结果。角色通过后端 `mail.manage` 受限工具读取和管理主人级邮件服务；即使邮件自动处理暂停，角色仍可查询、查看草稿并明确恢复服务。角色不能访问凭据、任意 IMAP 命令或发送/删除原邮件。每次角色操作记录角色、运行和结果，能力调用与工具结果不写作普通角色消息。

自动生成的草稿可以按批次汇总为指定提醒角色的一条主动消息。提醒只引用已确认写入 QQ 草稿箱的草稿，同时报告本批处理失败/待核实的邮件数量和可定位摘要；批次和投递状态持久化并去重，投递失败可重试，更换提醒角色不改变邮件或草稿。

## 7. 验收与限制

- #92–#98 的用户验收以真实 QQ 账号互操作测试、Python 测试和网页构建为准。
- 附件内容、附件复制、SMTP、自动发送、删除/归档/移动、外部系统通知不在本规格内。
- 当前模型和 QQ 网络依赖不可用时，系统必须保留可诊断的失败或待核实状态。
