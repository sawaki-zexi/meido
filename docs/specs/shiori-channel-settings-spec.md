# Shiori 多端配置与 QQ 扫码接入

状态：当前

最后核验：2026-10-25

事实来源：[Issue #134](https://github.com/sawaki-zexi/meido/issues/134)、[源码对照](../research/shiori-channel-settings-ux.md)、[多端会话规格](multichannel-conversations-spec.md)、[ADR-0010](../adr/0010-channel-lifecycle-and-managed-qq.md)、当前渠道 API 与前端流程测试。

## 用户流程

“多端连接”位于“设置 → 插件 → 服务与连接”；“我的身份”保留独立顶层入口。“多端连接”中的“平台总开关”按 Telegram、QQ、官方 QQBot 和飞书分别显示“已启用／已暂停”及“暂停／启用”按钮，展示配置账号数和连接数；关闭平台保留各角色账号的连接意愿、配置、凭据、身份及历史，恢复时只连接原先开启的账号。保存的暂停状态在重启后仍生效。总开关按平台控制全部角色，不提供跨所有平台的单一开关。

“我的身份”提供全局配对码，不要求先选择角色或平台。配对码显示剩余时间并可复制，10 分钟过期、生成新码后旧码失效、成功消费后收起。配对仍从任意已连接账号的私聊进行，不创建机器人账号，不选择角色，也不追溯授权旧消息。页面统一展示全部平台绑定及作用域，支持刷新和解绑。

角色资料页增加“账号”页签，每个平台显示一行账号摘要和连接状态，选择后打开详情。新建角色保存前没有账号管理入口。普通账号保留已有凭据字段和连接测试，已保存凭据不回显，留空不替换；连接配置按需展开，在线账号才出现私聊、适用的群聊规则和黑名单。平台暂停时保留详情查看和删除入口，并引导到全局设置恢复。

侧栏不提供跨角色的“手机会话”入口；角色聊天头部提供当前角色的只读“多端会话”入口。聊天仍从对应外部平台发送，网页会话页不提供渠道发言框或提醒目标配置。角色账号页始终提供“平台总开关”直达入口。渠道历史、群旁听管理和提醒目标管理接口继续保留。

多端会话使用聊天上方的手机浮窗，支持拖动；窗口尺寸变化后保持在可见范围内。手机里的设置与平台账号详情采用逐级页面导航，账号详情占用手机屏幕，不额外打开模态弹窗；返回账号列表时焦点回到刚才的平台。账号列表与暂停平台的详情均可直达全局平台总开关。进入手机设置再返回时保留选中会话、已加载消息和阅读位置。

手机采用 Shiori 的“主页 → 账号 App → 会话列表 → 单个聊天”逐页导航：主页按当前角色账号显示 QQ 等可点击的应用，设置作为同一网格最后一个入口，不在右上角重复放置设置。账号离线时仍可打开应用读取历史，并标明离线。未配置账号且没有历史时只显示居中的设置按钮，保留原账号配置流程。

首次读取失败时提供重新读取入口；关闭错误文案不改变加载状态，重试入口仍可使用，不显示没有请求进行的永久加载画面。

连接成功后仍停留在应用主页，不自动进入空白列表与详情分栏。点击账号 App 后只显示该账号的会话列表；没有消息时显示单页“还没有会话”，首条会话到达后实时更新，由用户点击进入聊天。聊天页只显示选中的时间线，返回依次到账号列表、主页和原角色聊天。设置与返回保留已加载分页及阅读位置；设置返回时刷新账号，刚配置的账号立即出现在主页。会话来源于已保存的渠道消息，不把平台好友／群目录当成聊天历史。

以上导航依据[Shiori 手机流程源码研究](../research/shiori-phone-connected-flow.md)。Meido 保留两项既有适配：设置页继续管理角色渠道账号；已移除账号的历史以独立的只读应用入口保留，和当前同平台账号隔离，不因导航改变而隐藏历史或重新归属。

消息展示依据[Shiori 消息源码研究](../research/shiori-channel-message-presentation.md)：会话列表使用头像、名称、简短时间与单行纯文本摘要，不重复展示账号来源和平台。聊天页将头像放在气泡外，来信显示发送者，角色回复靠右；首条有效时间和相邻有效消息间隔超过五分钟时集中显示时间。纯提及显示 @名称或平台 ID，引用在正文前默认折叠长内容，图片和文件位于正文后，图片支持放大与关闭。来源、完整时间及平台编号收进可展开详情。

Meido 保留实际回复与投递状态：生成失败展示失败原因，没有原因时显示“回复未能完成”；投递失败与结果不确定不冒充生成失败，不确定不能显示为已发送；部分生成失败且发生投递时同时保留两种状态。历史读取与实时消息更新均使用同一规则。只有非文本消息且没有可展示的提及、引用或附件时才使用非文本占位，不把纯提及、附件或失败记录显示为“无内容”。会话摘要去除 Markdown 标记，`failed` 状态使用“回复需关注”，因为当前摘要接口没有投递元数据，不能仅凭状态推定生成失败；没有发送者和附件元数据时不推测其身份或具体媒体类型。群旁听状态和只读边界保持可见。

从角色记忆定位渠道原文时，按需打开只读“记忆来源”弹窗，关闭后回到原记忆页。弹窗直接核验线程属于当前角色，不依赖账号或会话目录，支持普通消息与独立群旁听记录的跨页定位、媒体和来源信息；不显示账号、群旁听或提醒目标管理控件。

## QQ 接入

Windows x64 上新增 QQ 默认使用托管 NapCat。点击准备后后台下载并校验固定版本运行包，检测所需官方 QQ 运行环境，在独立目录创建本机连接配置和随机凭据，启动受管理进程，展示准备进度和官方登录二维码。用户扫码后，应用核验 OneBot 返回的真实 QQ 身份并确认账号归属，再保存角色账号；准备或登录不成功时不产生可用账号。

Windows 的开发重载服务使用不支持异步子进程的 SelectorEventLoop 时，QQ 通过文件日志进程启动，并沿用相同的挂起创建、Windows Job 归属后恢复及进程树清理；不改变其他功能的事件循环或管道处理。

二维码可刷新，准备或登录错误有可重试反馈；准备失败时不同时显示启动中、旧二维码或确认连接。取消临时登录、移除账号、删除角色、暂停渠道和退出应用会停止相应受管理进程，清理兼容 QQ 在 Windows 下创建的只读目录。已保存账号可保留登录状态并恢复连接，重新登录不能将原账号身份静默换成另一个 QQ。

现有外部 NapCat 账号继续可用，手动 WebSocket 配置作为兼容入口保留。托管服务只监听本机，公开响应不返回内部访问令牌或私有目录；安装验证摘要、压缩包路径和文件大小，不处理或终止用户自行启动的 QQ/NapCat。

当前运行包为 NapCat 4.18.28，始终使用包内 QQ 9.9.31-49738 的 wrapper。首次准备从已安装官方 QQ 中校验并复制缺失的 crypto.dll、ssl.dll 到私有托管目录；已验证的依赖摘要涵盖 QQ 9.9.31-49738 和 9.9.36-53644，只接受完整匹配的组件组合。之后启动重新校验私有缓存，不依赖桌面 QQ 当前版本，桌面更新或移除不影响已准备的缓存；损坏的缓存须从兼容安装重新准备，不接受未知摘要。复制与下载均受同一安装租约保护，取消须等待写入结束再释放租约。Windows x64 已实际验证新版 QQ 组件、官方二维码、取消与重试；真实扫码和平台权限仍需要人工环境核验，二维码测试不代表已完成真实账号收发。

## 验收边界

- 从全局设置与角色账号可完成接入和身份管理；每个平台的总开关有明确状态与操作文字，窄屏下控件与反馈可见。
- 侧栏无跨角色手机会话入口；角色聊天可打开只读多端会话页，渠道记忆仍通过只读弹窗定位原文。
- 平台暂停后不接受新的渠道回合或主动发送；已经启动的回合按既有收尾语义处理，等待角色锁的消息在启动前重新检查。
- 账号连接意愿与平台启停分开保存，重启、失败重试和恢复不会误启用已断开的账号。
- 配对码及身份仍由宿主授权；访客、主人、群聊和跨角色历史隔离不因界面迁移改变。
- QQ 归属、真实登录身份、临时会话、凭据与托管进程均由后端校验；前端参数不能绕过。
- 使用公开 HTTP 接口、用户操作流程及外部下载/进程边界验证；前后端测试、类型检查、构建和两轴评审完成后创建面向 main 的 PR。
