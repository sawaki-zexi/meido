# 邮件草稿发送副本关联

状态：当前；第一阶段已实现，真实 QQ 验收待执行。

最后核验：2026-10-24

事实来源：`backend/app/mail/{adapter,service,store,models}.py`、`tests/python/test_mail.py`、`tests/python/test_mail_assistance.py`、ADR-0008。

## 目标

主人在 QQ 网页端发送 Meido 创建的草稿后，Meido 能在后续同步中把已发送副本与原草稿版本关联起来；无法唯一确认时保留待核实状态，不把草稿消失误判为已发送。

## 范围与边界

- 仍只使用 SSL IMAP 读取收件箱、Sent 和草稿箱；Meido 不发送、删除、归档或移动邮件。
- Sent 首次读取使用有界 UID 窗口，后续按当前账号和文件夹复用 UID checkpoint 增量读取；仍未匹配的草稿另有独立的有界尾部重扫，不推进增量 checkpoint。
- 每个草稿版本拥有独立的发送关联记录；旧草稿、人工修改和追加版本互不覆盖。
- 发送关联只影响本地状态和展示，不触发自动发送或自动跟进。

## 状态

- `pending`：本次已成功读取 Sent，但尚未找到唯一副本；这不表示邮件一定没有发送。
- `matched`：找到唯一发送副本，保存 UID、Message-ID、时间和匹配依据。
- `ambiguous`：存在多个同等候选，不能猜测归属。
- `unknown`：Sent 读取或关联过程失败，保留错误并等待下次核对。

草稿仍在 QQ 草稿箱时，草稿状态继续反映草稿是否被主人修改；草稿从草稿箱消失且关联为 `matched` 时，草稿显示为已发送，来信状态变为 `sent`。没有唯一发送关联时仍按原有 `missing`/`uncertain` 规则处理。

## 匹配规则

候选必须来自主人账号发出的邮件，并且收件人和草稿收件人有精确地址交集。优先使用 Meido marker；没有 marker 时依次结合来信 Message-ID 对应的 `In-Reply-To`/`References`、草稿 Message-ID、规范化主题和正文片段。只有唯一最高分候选才能标记 `matched`；同分、多个候选或缺少必要身份信息时标记 `ambiguous` 或保留 `pending`。

## 验收

- 首次同步最多读取配置的 Sent 历史窗口，成功后保存最高 UID；后续读取只请求更大的 UID。
- 唯一 `In-Reply-To`、收件人、主题和正文候选会关联到正确草稿版本。
- 两个相同候选不会被猜测为已发送，关联状态为 `ambiguous`，来信保持待核实。
- 草稿被 QQ 移出草稿箱但存在唯一发送副本时，不显示为“已删除草稿”，而显示为已发送。
- Sent 读取失败不会推进 checkpoint，也不会覆盖收件箱同步进度；下一次同步可以重试。
- 首次窗口外的发送副本在草稿仍未匹配时可由周期性尾部重扫发现；重扫失败保留诊断状态并等待下一次重试。
- 账号切换后不能读取或更新另一个账号的发送关联。

## 后续

线程级 `to_reply`、`awaiting_reply`、关闭状态、到期时间和幂等提醒账本已在 [mail-followup-spec.md](mail-followup-spec.md) 中实现。当前支持主人明确触发的催复草稿，并提供默认关闭的到期自动催复草稿开关；两者都沿用发送副本核验、版本保护和未知 APPEND 对账边界，最终发送仍由主人在 QQ 完成。
