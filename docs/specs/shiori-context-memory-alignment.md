# Shiori 上下文与记忆全链路对齐规格

状态：当前；维护者已批准，由 [#302](https://github.com/sawaki-zexi/meido/issues/302) 实施。
最后核验：2026-11-02。
事实来源：用户“全部向 shiori 靠齐”；[完整调研](../research/shiori-context-memory-20261102.md)及其固定源码链接、隔离探针；已有父规格 [#279](https://github.com/sawaki-zexi/meido/issues/279)。
固定基线：Shiori `c14152ed225954a2a50da775075fe64dbf7b8b50`；Meido `69b9c4a6f3aaeb3b3cc74c39a679822c3c6d9e10`。

## Problem Statement

长对话回复仍可能在准备、记忆维护和失败压缩中等待很久。既有实现分别引入了摘要、记忆、用量校准和工具恢复，却在请求排列、读写职责、提交条件及失败行为上保留了另一套规则。摘要未成功提交时，下一轮再次面对原来的大窗口；此前关闭记忆的端到端不能证明真实路径可用。

## Solution

按固定 Shiori 的上下文与记忆架构统一整个对话链路：普通请求读取已保存的合法窗口，稳定提示和动态上下文各就其位；只有容量触发或明确手动压缩才尝试工作摘要。后台维护、压缩必需的记忆覆盖、后续消费者各自按上游边界推进，失败和恢复行为也对齐。

本轮包含调研列出的上下文/记忆差异及其在桌面、渠道、旁听、主动任务和子代理中的消费者。此前特意保留的 minimal 业务工具、全局记忆耦合、结构化记录与文档强同步、向量空间自动重建等差异，不再作为目标语义保留。手动压缩入口纳入本次。

按用户先前明确要求，**一个实施 Issue、一个集成分支、一个 PR**。内部按可验证里程碑推进，不再拆成一串分别合并的后续票。

## User Stories

1. 作为主人，我希望普通消息使用已保存的摘要与原文窗口，而不是每轮再次总结已处理的历史。
2. 作为主人，我希望正常检索只等本次查询所需工作，不等库内缺失向量补建。
3. 作为主人，我希望稳定角色记忆和历史形成稳定请求前缀，动态信息按 Shiori 放置。
4. 作为主人，我希望达到容量阈值后才工作压缩，已保存的结果在下一轮和重启后继续使用。
5. 作为主人，我希望原文移出输入前完成必要记忆整理，摘要失败也不重复已经成功的记忆提取。
6. 作为主人，我希望下游消费者失败可独立恢复，不把已经落盘的记忆当成尚未保存。
7. 作为主人，我希望并发追加消息不废弃不受影响的旧前缀，而编辑、撤销或身份变化正确失效相应结果。
8. 作为主人，我希望压缩失败、硬超限和最小请求的工具行为与 Shiori 一致，不悄悄换成另一种回复语义。
9. 作为主人，我希望角色文档、语义记忆引擎和周期优化各有清晰责任，开关和错误不再相互混淆。
10. 作为主人，我希望既有 SELF、MEMORY、候选、经历、结构化记忆及来源在升级后保留。
11. 作为主人，我希望记住、忘记和回忆工具的可用性、说明、参数与实际引擎能力一致。
12. 作为主人，我希望当前上下文的独立检查和手动压缩入口像 Shiori，草稿不被提交或丢失。
13. 作为主人，我希望桌面、主人私聊、群聊、陌生私聊及旁听采用同一套来源边界。
14. 作为主人，我希望后台优化、主动任务和子代理不会混入普通回复的历史或用量。
15. 作为主人，我希望回复期间仍能切页、刷新续接和明确停止，并通过记忆开启的浏览器端到端验证。

## Implementation Decisions

### 1. 以行为和数据责任对齐，使用一个实际请求来源

- 固定上述 Shiori 提交作为本 PR 的唯一比较基线，不在实施中追逐 upstream main。
- 普通被动回复采用稳定 system → 合法历史/工作摘要 → 动态 context frame → 当前输入及本轮后续工具交换；手动检查不创建虚构当前用户消息。
- SELF/MEMORY 按上游范围和全文读取规则进入稳定提示；近期语境去掉重复原文后与检索结果、状态等进入动态 frame。不再用 Meido 自有 4000 字符合并视图截断固定文档。
- 普通发送、候选测量、独立检查、手动压缩共用实际请求组装和规范化入口；不为圆环创建另一份上下文真相。
- 读取路径不刷新文档、不补建库内向量、不触发长期优化。已有 actual/anchor_delta/local 用量逻辑复用，并验证新排列后的失效边界。
- 不新增本地 KV 管理器。稳定前缀与供应商原生缓存指标按上游使用；缓存 token 仍参与上下文容量。

### 2. 工作窗口与记忆进度独立持久化

- 会话层拥有原文身份、可见视图、工作摘要/切点和维护进度。Markdown 整理游标、窗口切点、消费者进度不能互相替代。
- 将记忆游标与待处理消费者归到会话维护所有者，停止依赖“临时维护返回成功”证明覆盖；旧分散进度一次迁入，不新增平行权威数据库。
- 普通积压按上游阈值入后台队列；已有明确维护失败按上游入口处理；真正移出具体前缀时等待其覆盖，不先按任意消息条数阻塞每个回复。
- 自动工作压缩先持久记忆覆盖，再生成/校验分批工作摘要，最后在同一提交中发布摘要和切点。使用上游完整轮次选择与软/硬容量边界。
- 后续事件发布和关系消费者保存各自进度及 payload；失败后可恢复。已覆盖的原文不因 pending consumer 被当作未整理；已经发布的事件不重复发布。
- 校验冻结前缀和实际身份、版本，允许该前缀外合法追加；已覆盖原文编辑、撤销、解绑、角色删除仍使相关派生状态失效。
- 取消等待已开始提交结束，不留下终态后继续改写窗口的任务；重启恢复已提交进度，不假装续跑已失去的模型流。

### 3. 失败行为和工具窗口按上游收敛

- 未到软阈值不调用工作摘要；软阈值压缩失败且原请求低于硬上限时，本轮继续原输入，下轮可再尝试。
- 硬超限中的记忆/摘要阶段失败按上游返回，不统一吞掉后用 minimal 回复。
- 只有上游允许的缩减路径进入 minimal；业务工具不提供，必需回复协议和完整当前输入/已执行结果保留。此项明确替代此前 #277/#279 的“minimal 保留业务工具”决定。
- 供应商真实上下文溢出使用上游有界重试，不重放已经执行的业务副作用。摘要仍分批、只允许一次合法超长缩短，不增加跨回合永久熔断或自定义冷却。
- 工具由当前注册表执行；常驻和延迟工具的声明、解锁恢复与当前原文窗口一致。记忆工具由当前引擎 profile 注册，不因旧缓存或提示宣称虚假可用。

### 4. Markdown、默认语义引擎与优化器分别负责

- Markdown 为宿主角色文档层；默认语义引擎是独立可用/不可用的能力；周期优化为独立调度。关闭语义引擎不再一并停止宿主文档整理。界面与配置名称表达这个真实边界，避免保留误导的“全局记忆总开关”含义。
- 采用上游规范文档结构、用户/外部可见段落、HISTORY/PENDING 来源防重、近期语境来源标记及快照恢复行为。
- MEMORY/SELF 不再由结构化库每次管理操作整体重投影；语义库与文档分别承担上游职责。记住/忘记/文档编辑走各自真实入口，不制造删除一条结构化记录就已清除所有文档叙述的假象。
- 周期优化按上游默认周期、PENDING snapshot、SELF 写作规则、成功/失败/取消恢复执行，不与查询或全部后处理共用长时间持有的角色锁。既有用户设置保留，缺省值按基线。
- 不因“解耦”取消已有来源与角色约束；允许范围按上游用户/外部语义判断，不靠模型自报来源。

### 5. 语义写入、检索、配置生命周期对齐

- 默认引擎拥有自己的 embedding 配置和向量空间指纹。凭据缺失或已存在模型/维度不匹配时明确不可用；不借用聊天凭据，不在检索时自动清除旧空间并回填。
- 新显式记忆沿用上游 embedding-first；写入失败不能返回记住成功。已有无向量记录不删除，也不在普通读取里偷偷修复。
- context/procedure、answer、timeline、interest 的分流，HyDE 调用边界、超时、RRF 权重、类型阈值、配额、热度、文本预算与 procedure guard 按当前上游配置和实现对齐，不沿用 Meido 的近似排名充当等价。
- 回合后处理和 ConsolidationCommitted 消费按上游来源、类型、显式记忆保护、替代与防重规则执行；真实失败按对应路径呈现，不额外承诺上游没有保证的事务性。
- memorize/forget_memory/recall_memory 常驻条件、工具说明、参数及实际执行共用当前引擎能力；不再让全局提示和真实 schema 矛盾。

### 6. 多场景消费者与手动入口

- 主人上下文、外部上下文、群成员/群动态及用户本人群发言分别采用上游范围与游标语义；不混淆外部用户与主人身份。
- 旁听独立游标、按群 50 条/跨天批次、入库触发及启动/周期扫查按上游接入同一整理逻辑；不影响角色会话整理游标或用户近期语境。
- 主动/Drift 采用其上游临时上下文，不强行套普通聊天；子代理保持独立历史、用量和结果保存责任。本轮迁移这些场景的上下文/记忆调用，不重写无关投递和任务功能。
- 引入 Shiori 式手动压缩：圆环入口及 `/compact` 使用相同上下文控制，忙碌、未知、失败如实展示；不发送草稿、不新增长对话中的普通聊天回合。
- 圆环只保留上游交互与视觉，不增加预算调试面板、阶段列表、重查按钮或另一套进度界面。

### 7. 数据与设置迁移

- 迁移仅在开发夹具和独立数据上验证；本 PR 不自动部署，也不迁移正在运行的正式实例。
- 现有消息 ID、来源、角色、账号、线程关系不重写为伪造的新事实；物理存储适配可以保留，行为和进度责任必须一致。
- 合法摘要/切点、记忆游标、待处理事件和 provenance 能证明等价时迁入；不能证明来源的旧派生数据留存归档，但不标记为新来源或已完成覆盖。重新启动迁移不重复消费。
- 原始 Markdown、候选 snapshot 和结构化记录均保留。已有托管区内容迁为普通文档内容，不清空手工文本；规范段落不能由无证据猜测填充。外部上下文只读可证明合法的规范段落。
- 迁移后停止旧正常写路径，不维持两套持续同步机制；旧格式只在兼容导入/恢复边界读取，提供可执行回滚步骤与迁移前备份。
- 既有明确的开启/关闭意愿映射到对应引擎/优化器设置，不自动开启账号、旁听群、主动功能或外部工具许可。宿主文档维护独立运行属于本次明确对齐的行为，可能产生相应模型调用；配置说明需清楚。
- 已有向量空间不被自动重写；不能验证指纹时保留数据并报告引擎不可用，而不是为通过迁移发起真实模型请求。

## Testing Decisions

1. 最高验收入口为真实浏览器 → 实际 HTTP/SSE 服务 → 实际会话/文档/语义存储 → 本地受控模型与 embedding HTTP 服务。**启用记忆与优化器相关路径**，不以关闭功能换取流畅结果。
2. 通过供应商请求记录、可见界面、持久状态和重启后的行为判断；不编写仅镜像私有函数结构的测试。既有上下文、记忆、模型协议、渠道和浏览器测试尽量复用。
3. 新关键行为先红后绿：查询不补建、未达阈值不摘要、记忆先于摘要、消费者失败不挡已覆盖窗口、合法追加可提交、硬失败不吞、minimal 工具、手动压缩与草稿保留。
4. 差异验证使用固定 Shiori 的同源行为夹具；数据库实现不同可通过适配比较输入、事件顺序、持久结果和错误，不要求照搬上游测试的私有类型。
5. 覆盖迁移中断/再启动、旧 pending event、旧合法/过期摘要、已有手工文档、缺失向量和错误指纹、角色/身份变更；原始数据数量与内容不得静默减少。
6. 浏览器场景覆盖短对话、首次越阈值、下一轮复用、重启复用、多批失败、消费者故障恢复、工具跨阈值、切页/刷新/停止、手动压缩、引擎不可用但文档正常、多角色及外部隔离。
7. 本地慢模型和慢 embedding 以可控挂起点运行，期间设置/插件等页面能正常访问；分开记录本地准备、检索、记忆提取、工作摘要、模型首输出、工具执行及提交耗时。供应商等待不能冒充本地性能，也不能用 minimal 的实际输入替代完整窗口估算。
8. 运行受影响测试、类型检查、构建与 CI，并按仓库规范/本规格独立审查；复用未变化的通过证据。上游已知资源关闭警告如实记录，不屏蔽后宣称全绿。

## Out of Scope

本轮“全部”限定为刚完成调研的上下文与记忆架构以及相应工具、界面入口和消费者，不扩展成重写 Meido 的整个插件内核、所有业务工具、渠道协议或桌面平台。现有 Web 后端持有回复与刷新续接保留，并与新数据流集成；多模型协议适配保留。

不新增自建 KV 服务、第二套记忆权威库、永久失败冷却、调试圆环面板；不删除旧消息和手工记忆，不进行真实渠道或付费模型验收，不未经批准合并、部署或关闭 Issue。
