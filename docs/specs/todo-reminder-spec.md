## 1. 目标

待办是主人的共享清单。主人可以在任一角色对话中自然表达创建、修改、完成、取消或恢复待办的请求，由角色调用待办工具完成；也可以在网页上直接管理全部待办。两种入口共用同一待办应用服务和校验规则。

提醒由角色主动发送：每天按主人时区 04:00，由当天选定的提醒角色发送今天的待办汇总；待办指定精确时间后，到点再由同一角色发送单项提醒。提醒文字结合角色人格和相关记忆生成，但待办事实始终来自待办数据。

待办作为一个可启停的应用级插件存在。插件拥有待办状态、工具适配、调度和消息接入；Agent Tools 是角色使用该插件的入口，不是待办权限规则本身。

## 2. 架构流程

```text
角色对话 ── Agent Runtime ── todo.write ─┐
网页待办 ── HTTP API ────────────────────┴─> 待办应用服务 ─> 待办存储
                                                   │
                                                   └─统一校验、状态转换和来源记录

提醒调度器 ─> 读取待办数据 ─> 选定的当日角色生成消息 ─> 角色会话中的主动提醒消息
```

待办写入由模型提出结构化操作，后端应用服务负责校验和持久化。前端和角色工具不能各自实现一套写入逻辑。提醒调度器不从对话猜待办，也不允许角色记忆覆盖待办内容。

## 3. 范围

包含：

- `todo.write`：创建、修改、完成、取消和恢复主人待办；任何角色都可以调用。
- `todo.search`：可选的只读查询能力，供角色回答待办相关问题。
- `todo.reminder_control`：当前角色加入或退出提醒角色列表，以及根据主人明确指令暂停当天提醒。
- 网页待办清单的完整查看和编辑能力，以及提醒角色配置和当天提醒暂停入口。
- 每日 04:00 汇总、精确时间提醒、当日提醒角色持久选择和失败诊断。
- 角色主动消息的生成、会话持久化和去重。

不包含：

- 循环待办、子任务、多人协作或远程插件安装。
- 邮件、操作系统通知或其他外部通知渠道。
- Meido 关闭期间准时发送消息的保证；恢复后只按持久化调度状态处理仍有效的任务。

## 4. 待办工具和写入规则

角色通过 `todo.write` 表达待办操作。该工具处理自然语言请求转成的结构化操作，不使用正则表达式决定是否允许模型调用工具。普通分享或假设性表达不应被角色当作明确待办请求。

`todo.write` 支持创建、修改、完成、取消和恢复。角色可以协助管理主人清单；网页也保留完整的待办编辑权限。所有写入均经过同一个待办应用服务，校验字段、当前主人范围、目标唯一性、状态转换和幂等性。模型不能直接写数据库、选择其他主人或绕过这些校验。

目标待办无法唯一确定时，不修改任何事项，应向主人澄清。明确事项没有日期时进入收件箱；仅给出日期时保存日期，不补造具体钟点；只有主人给出精确时间时才建立精确时间提醒。相似请求不能重复创建同一活动事项。

`todo.reminder_control` 的角色范围受限：角色只能将自己加入或移出提醒角色列表，不能替其他角色操作。加入或退出从次日生效，不改变已经固定的当日提醒角色。暂停当天提醒是主人级操作，角色只能在主人明确提出后代为执行。

| 操作 | 作用范围 | 生效时间 |
| --- | --- | --- |
| `join` | 当前角色加入提醒列表 | 主人时区的次日 |
| `leave` | 当前角色退出提醒列表 | 主人时区的次日 |
| `pause_today` | 主人当天的全部提醒 | 立即；次日自动恢复 |
| `resume_today` | 恢复主人当天的后续提醒 | 立即 |

任意角色都可以按主人明确请求暂停或恢复当天提醒，不要求该角色已加入提醒列表。加入、退出和当天暂停都不影响角色创建或修改待办的能力。

## 5. 提醒角色选择

主人可以在网页上维护一个或多个启用提醒职责的角色；角色也可以按上述规则管理自己的资格。每天按主人本地日期，从当前可用的提醒角色中随机选择一位，并持久化当日选择。

一旦选定，当天的每日汇总和所有精确时间提醒都由同一角色发送。不能为每条提醒重新随机选角。当天角色被删除或禁用时，从其他可用提醒角色中重新选择并保存；没有可用角色时，当天不发送任何提醒。

删除或禁用属于角色立即失效，与正常加入或退出列表的次日生效规则不同。重选只接管尚未发送的提醒，不能重复发送已成功投递的汇总或单项提醒。

每日 04:00 汇总包含当天需要处理的有效待办。设置了精确时间的待办仍会在指定时间单独提醒；它也可以出现在当天汇总中。没有需要处理的事项时不发送空汇总。

## 6. 提醒生成与投递

每日汇总按主人 IANA 时区的本地 04:00 触发。精确提醒按待办保存的绝对时间触发。日期型待办不能被擅自解释为精确时间。

生成消息时，系统向当天提醒角色提供真实待办标题、日期、状态等必要事实，并结合该角色的人格设定和相关记忆组织自然表达。角色负责表达方式，不负责从记忆推断、改写或新增待办事实。

提醒任务、当日角色和投递结果必须可持久恢复并去重。同一日期的汇总和同一待办的同一精确提醒不能重复发送。完成或取消的待办不再触发尚未发送的提醒。投递失败应保留诊断并可重试；Meido 关闭期间不承诺准时触发。

## 7. 主动消息边界

成功提醒以当天提醒角色的主动消息写入该角色会话，并标记为 `proactive_reminder`。它应显示为角色发出的消息，但不能构成新的用户回合，不能再次触发待办整理，也不能进入记忆整理输入。

主动提醒只带入实际需要的待办事实及生成消息所需的人格、记忆上下文。不能把全部待办清单写入角色记忆，也不能把提醒内容当作主人说过的话。

## 8. 数据归属与模块边界

待办属于主人，不属于创建它的角色或会话。来源角色、会话和消息用于追溯；删除角色不会删除待办。提醒角色配置和每日角色选择属于提醒调度状态，与待办状态分开维护。

TodoPlugin 由应用生命周期启动和关闭，管理待办存储、应用服务、工具适配器和提醒调度。Agent Runtime 只通过受限的待办工具端口操作待办；网页 API 调用同一应用服务。调度器从已保存的待办读取数据，再通过主动消息边界调用当天角色。这个模块不依赖 MemoryStore/MemoryEngine 的内部表。

## 9. 前端行为

聊天页继续提供待办抽屉，用户可创建、编辑、完成、取消、恢复待办并查看来源和提醒状态。设置页允许用户启用或移除提醒角色、暂停当天提醒，并显示当前提醒状态。

暂停当天提醒会立即跳过当天尚未发送的每日汇总和精确时间提醒，不删除待办、不修改提醒时间；次日自动恢复。加入或退出提醒角色从次日生效。没有启用提醒角色时显示未配置状态，系统不发送提醒。

当天主动恢复后，后续到点的提醒继续执行；暂停期间已跳过的提醒不集中补发，次日也不补发。设置页应区分插件启停、角色提醒资格和当天暂停状态，避免将暂停提醒误当作禁止待办编辑。

## 10. 验收标准

1. 在任意角色对话中明确要求创建或修改待办时，角色可通过 `todo.write` 完成操作；普通分享不会自动创建待办。
2. 角色工具和网页对同一待办的修改结果一致；两种入口遵守相同字段、归属、目标匹配和状态转换规则。
3. 目标不明确时不会静默修改错误待办；日期请求不会被补成未表达的精确时间。
4. 用户可配置多个提醒角色；每天只随机选择并持久化一位角色，当天所有提醒由该角色负责。
5. 当日角色被删除或禁用后立即重新选择其他可用角色；没有可用角色时不发送提醒，重选不重复投递已成功发送的提醒。
6. 当地时间每天 04:00，角色以主动消息发送当天待办汇总；无待办时不发送空汇总。
7. 有精确提醒时间的待办会在该时间由同一当日角色发送单项提醒。
8. 主人明确要求角色加入或退出提醒角色时，只改变当前角色资格并从次日生效；角色不能代替其他角色修改资格。
9. 主人明确要求停止当天提醒后，当天汇总和所有精确时间提醒均暂停，次日自动恢复，待办及提醒时间不变；当天恢复后只继续后续提醒，不补发暂停期间已跳过的提醒。
10. 提醒消息以角色消息显示，类型为 `proactive_reminder`；它不成为用户回合、不触发待办整理且不进入记忆输入。
11. 调度和消息生成在失败或进程重启后可诊断、可恢复且不会重复发送；应用停机期间不承诺准时提醒。

## 11. 验证重点

测试应覆盖角色工具与网页共用写入规则、歧义操作拒绝、提醒角色资格变更、每日角色固定和重选、时区边界、04:00 汇总、精确提醒、当天暂停与次日恢复、主动消息去重，以及主动消息与用户回合/记忆整理的隔离。
