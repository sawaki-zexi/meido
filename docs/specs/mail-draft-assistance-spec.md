# 邮件草稿准备与补充确认

状态：当前；#201 实现已通过合成邮箱与模型验证，真实 QQ 验收待执行。

最后核验：2026-10-24

需求来源：#200、#201，以及本会话中对邮件深度调研第一阶段的实施授权。

事实来源：现有邮件模块、邮件集成规格、ADR-0008；新增行为以本票测试和验收结果为准。

## 用户结果与范围

主人从网页或获准角色准备 QQ 回复时，系统参考当前往来、同对象已发送回复和保存的主人写作偏好；需要主人决定时保存问题，补充后继续起草。详情展示实际提供给模型的来源与上下文读取失败项。最终审核发送仍在 QQ 邮箱完成。

只增强现有本地邮件模块，复用 SQLite、持久任务和草稿版本规则。一次模型调用可同时返回判定和可选正文。双向跟进、附件、自动风格学习、其他邮箱和发送/删除/归档/移动不在本期。

## 相关往来与偏好

起草时按规范化对象地址从已发送文件夹有界检索，最多读取 24 封匹配邮件；校验实际收件对象后导入本地线程，保留回复头、时间、方向和来源身份。线程与样本分开：当前往来最多八封，同对象额外样本最多三封。文件夹副本按当前账号和 Message-ID 去重；自己已发送的记录不进入来信列表与自动处理。该读取按需进行，不新增全邮箱持续扫描或已发送 checkpoint。

写作偏好为主人级文字配置，限 2000 字符，重启保持，角色更换不改变偏好。网页另提供默认关闭的“允许角色管理邮件”许可；只有已验证连接和该许可同时具备时，主人上下文的 mail.manage 才获运行批准。撤销许可使后续工具调用被拒绝；访客不继承批准。不删除工具原有 approval 声明。

## 判定、补充与恢复

结果分为 no_reply、needs_input、draft，携带原因；needs_input 必须有非空具体问题，draft 必须有正文。保留读取旧 needsReply/body 结果的兼容路径，显式矛盾或无效结果失败，不能当成无需回复。

每次准备保存来源账号范围、账号连接代次、邮件、任务键、线程内容指纹、原因、问题、来源清单、降级项、模型身份、生成时间和正文。待补状态不参与自动重复处理。问题 ID 固定到该次准备；网页/角色提交答案必须携带问题 ID 和请求 ID。答案持久化到任务输入，重启可以续办；相同请求相同内容返回原任务，不同内容拒绝。执行前补查来信和相关已发送往来，账号切换或连接代次改变则拒绝旧问题；已保存答案但尚未写入远端的恢复也须重新验证原问题和线程指纹；已经完成的原请求重放只返回原结果，不重复生成。角色任务固定携带可信角色/运行来源，入队后若许可撤销，worker 写入前拒绝执行。

准备结果同时记录模型配置稳定 ID、输入 prompt 哈希、消息数量、输入字符量、输出字符数和模型耗时。单次模型输入总字符数不得超过 36,000；超预算时按旧线程、主人资料、历史样本、当前正文的顺序压缩，并同步更新来源中的实际提供字符数和截断标记。哈希只用于确认同一输入版本，不把邮件全文写入普通日志；流水线版本变化时递增 `pipelineVersion`。

补充产生新的稳定任务键和草稿 marker，复用原远端回读及未知结果恢复。每封来信的草稿版本有稳定递增序号，详情显示序号、状态和各自来源；旧数据迁移时按创建时间与 ID 稳定补序号。任务持久记录是否已经进入远端 APPEND 阶段：只有确认尚未开始远端写入的任务可以自动重试；APPEND 已开始但结果未知时，只能用原 marker 对账，不得因一次未查到 marker 就再次追加。恢复的旧版“运行中/不确定”任务按可能已写入处理。普通同步/重试不覆盖人工草稿；取消不能自动补建未知远端写入。主人明确要求创建新版本时使用独立请求键和 marker。

详情在存在可能已经 APPEND 但本地未确认的任务时返回 `unconfirmedAppend`。网页和角色入口的普通重试只执行原 marker 对账，不调用模型也不追加；远端仍不可见时，创建独立草稿版本必须携带主人明确确认。对账找到原草稿后先保存原版本，再允许生成新的版本；若仍不可见，新版本结果继续显示原写入可能存在，提醒主人在 QQ 草稿箱复核。

自动后台对账使用持久化的最近核对时间、下次核对时间和次数，并采用有上限的退避；主人主动点击核对时可以立即读取。任务 worker 只领取当前账号和连接代次的任务，旧账号任务在领取前标记为失效。

## 来源展示与提醒

来源由应用实际选取的输入构造，保留邮件/资料 ID、标题、时间或位置及可用的安全链接；记录截断的原文/提供字符数、已去除引用内容和读取失败；当前来信只注入一次，线程上下文仅包含该来信之前的邮件，按解析后的 UTC 时间从旧到新排序，同一时间用 Message-ID 和本地邮件 ID 稳定排序。引用清理只识别明确引用标记或完整引用头，避免仅因正文出现 `From:` 等文本而截断。每个准备结果还保存 provider、模型、流水线版本和真实可用/注入数量，便于解释生成时实际使用的输入。展示名称为“提供给模型的资料”，不宣称模型采用了每条来源或事实已经核验。模型不能指定任意来源链接；普通日志不复制完整上下文。来源关联生成记录/草稿版本，避免后来生成覆盖旧版本来源。

待补问题经指定提醒角色汇总提醒一次，问题可在邮件页定位；已有草稿批次提醒继续复用，不让待补问题冒充已创建草稿。

## 数据流与检查

受控入口 → 持久任务或已有角色查询 → 账号邮件与有界历史/资料/偏好 → 结构化判断 → 保存准备结果 → 无需回复/等待主人/原 QQ 草稿写入与回读 → 详情与批次提醒。

验证入口为已讨论的 HTTP 邮件接口、网页公开操作和角色能力装配。外部 IMAP/模型使用替身；真实 SQLite、任务、解析、权限和版本逻辑参与测试。逐个红-绿覆盖偏好保存/许可撤销、较老相关历史/线程/方向、三态与重启续办/过期/重放、来源与失败展示、人工草稿保护及原邮件回归。运行相关 Python/前端测试、TypeScript 和构建，再按仓库规范与需求规格分别审查。

邮件回复质量另有固定离线夹具 `tests/fixtures/mail_quality_cases.json`，通过真实本地邮件服务回放主人决定、无需回复、已知事实和写作上下文场景。夹具结果只验证流程和结果契约；真实模型的回复质量仍须使用同一输入记录模型、Prompt 哈希、耗时和人工抽检。

主要风险是自发信误处理、问题版本失效、账号切换和外部写入不确定性；使用方向筛选、账号范围/代次、线程指纹、稳定请求键和写前重新核对限制。新增存储采用兼容增量迁移，不删除原数据；不引入新事务宿主或宽权限邮箱接口。
