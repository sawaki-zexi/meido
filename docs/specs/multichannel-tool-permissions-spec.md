## Problem Statement

Agent 运行在主人电脑上，拥有主人记忆和本地工具。群友或未配对访客发起请求时，不能因为请求最终由同一台机器处理，就自动获得主人级数据和工具权限。

当前能力目录主要按角色、启用状态、风险和批准状态解析，缺少一个轻量的“外部请求是否可以使用此工具”边界。若只在提示词中提醒模型，模型仍可能看见不应展示的工具 schema，伪造参数也可能绕过模型层约束。

需要一个与 Shiori 相同方向的最小策略：宿主在入口确认身份；上下文先决定可见数据；工具通过一个显式标记同时限制模型可见性和服务端执行。这个策略要支持已配对主人在群里使用主人级工具，同时保持群上下文的可见范围不变。

## Solution

每轮请求由宿主构造不可变的权限上下文，至少包含：

- `sender_is_owner`：由已保存的身份绑定重新计算，不能由平台插件、消息正文或模型声明；
- `account_full_tools`：账号策略是否允许本轮主人级工具；
- `context_kind`：`owner` 或 `external`；
- 当前角色、账号、线程、群和发送者的可信作用域。

权限上下文按以下规则计算：

| 请求来源 | 数据可见范围 | 工具范围 |
| --- | --- | --- |
| 桌面或已配对主人私聊 | 主人上下文及当前请求允许的主人资料 | 当前角色已启用且通过普通批准策略的工具 |
| 已配对主人群聊 | 当前群线程和当前群允许的资料 | 当前角色已启用且通过普通批准策略的主人级工具 |
| 未配对私聊 | 当前外部私聊线程 | `external_allowed=true` 的工具 |
| 群友群聊 | 当前群线程和当前群允许的资料 | `external_allowed=true` 的工具 |

主人在群里的请求可以获得主人级工具，但不能因此读取桌面、主人私聊、其他群或主人私有记忆。`account_full_tools` 只改变本轮工具范围，不把群线程提升为主人上下文。

每个工具增加一个机器可读的 `external_allowed` 属性。对于 `external` 请求：

1. 能力解析阶段只向模型暴露标记为 `external_allowed` 的工具；
2. 工具调用阶段再次检查同一标记；
3. 工具发现只返回外部请求可以看到的工具；
4. 模型提供的线程、群、账号、成员或附件路径不能扩大宿主已经确定的作用域。

需要收窄参数的工具使用宿主约束，而不是新增完整权限图。例如消息查询只能查询当前外部线程，成员查询只能查询当前群，附件读取只能读取当前消息或引用消息中的附件，消息投递只能解析到已允许的目标目录项。

首期外部工具白名单为：

- `web_search`；
- `web_fetch`；
- `tool_search`，但只发现外部可用工具；
- `search_messages`；
- `fetch_messages`；
- `lookup_member`；
- 当前消息或引用消息的 `read_attachment`。

已安装且角色已启用的图片生成工具可以单独声明 `external_allowed=true`，但必须继续遵守角色级启用、额度、超时和平台投递策略。它不是默认开放本地文件、浏览器、桌面或外部账号操作的理由。

默认不向外部请求开放：Shell、本地文件读写、浏览器/桌面/屏幕控制、主人记忆和主人资料、待办与日程、群旁听开关、群上下文写入、MCP 管理、任意账号投递、子 Agent 委托和其他未显式标记的插件工具。

## User Stories

1. 作为已配对主人，我希望在私聊中继续使用角色已启用的主人级工具，以便多端会话保持与桌面一致的能力。
2. 作为已配对主人，我希望在群里请求角色执行任务，以便角色可以完成主人要求，同时不会把其他群或私人资料带入群聊。
3. 作为群友，我希望可以让角色搜索公开网页，以便获得普通信息帮助。
4. 作为群友，我希望角色可以查询当前群的有限历史和成员信息，以便继续当前讨论，但不能读取其他群或主人私聊。
5. 作为群友，我希望角色可以读取我在当前消息中发送的附件，以便回答附件内容相关的问题，但不能浏览主人电脑上的任意文件。
6. 作为主人，我希望工具权限在模型看到 schema 前就已收窄，以便提示注入或模型误判不能把隐藏工具变成可调用工具。
7. 作为维护者，我希望模型伪造线程、群、账号、成员或附件参数时仍被宿主拒绝，以便权限不依赖模型是否遵守提示。
8. 作为维护者，我希望同一工具在 schema 过滤和执行入口使用同一策略快照，以便不会出现“模型看不到但执行能调用”或“模型看得到但执行绕过”的不一致。
9. 作为维护者，我希望新增工具默认不对外部请求开放，以便新插件不会因为注册成功而意外扩大群友权限。
10. 作为主人，我希望解绑身份后后续请求立即回到外部工具范围，以便身份变更不会继续沿用旧权限。
11. 作为维护者，我希望群友请求失败时返回稳定的权限错误，而不是伪装成工具不存在或执行成功，以便页面、日志和测试可以区分拒绝原因。
12. 作为维护者，我希望工具搜索结果不泄露隐藏工具的参数、凭据或本地路径，以便“能发现”本身不会成为信息泄露渠道。

## Implementation Decisions

### 1. 采用单一外部工具标记

工具定义增加 `external_allowed`，默认值为 `false`。它只表达“非主人外部回合是否可以使用”，不替代已有的风险、启用、曝光、批准、来源和版本策略。最终工具集合仍是这些策略的交集。

不新增通用能力图、数据污染标签、委托令牌或多级角色继承。当前需求只需要区分主人回合和外部回合，并在工具参数上保持当前作用域。

### 2. 权限判断只信任宿主入口

渠道适配器只能提供平台事实，例如账号、聊天、发送者、群、引用和附件。宿主根据身份存储重新计算 `sender_is_owner`，并生成本轮权限上下文。插件字段、消息正文、引用内容、网页、图片文字和模型输出都不能授予主人权限。

配对码的生成、十分钟有效期、一次性消费和解绑沿用多端会话规格；本规格只消费配对结果，不创建第二份身份状态。

### 3. 权限上下文先于检索和推理

上下文构建先得到当前请求可读的线程、消息、群资料和记忆范围，再执行历史检索、排序、摘要和模型输入装配。外部请求不能先看到主人资料，再依赖提示词要求模型不引用。

群中识别为主人的请求仍只读取当前群的原始聊天。群资料可以按当前群规则提供；主人私聊、桌面历史、其他群资料和主人私有记忆不因 `account_full_tools` 自动加入。

### 4. Schema 和执行双重检查

能力解析接收本轮权限上下文，过滤模型可见工具并在快照中记录拒绝原因。工具调用执行前使用同一快照重新确认工具存在、来源、启用状态、普通批准状态和 `external_allowed`。快照冻结后，本轮不能因配置或插件回调改变已解析的工具集合。

执行入口应把宿主确定的作用域放进 `ToolContext` 或等价的运行上下文，并覆盖模型传入的同名范围参数。工具不能通过读取原始 `session_key`、`thread_id`、`role_id` 或本地路径自行扩大范围。

### 5. 有限的参数约束

首期只为有明确跨目标风险的工具增加参数约束：

- `search_messages`、`fetch_messages`：忽略模型传入的线程范围，使用当前 `ContextView`；
- `lookup_member`：外部请求固定查询当前群；
- `read_attachment`：只接受宿主登记的当前/引用消息附件；
- `account_send`：外部请求不开放；如未来开放，只能使用宿主返回的目标目录项，不能接收任意平台 ID；
- `tool_search`：搜索结果与当前请求可见工具集合相交。

工具执行失败要返回稳定的 `permission_denied`、`scope_denied` 或等价错误类别，并保留不包含敏感参数的诊断信息。

### 6. 与现有能力解析兼容

现有角色级启用工具、风险过滤、曝光、批准和插件来源校验继续保留。外部工具过滤放在这些普通策略之后或作为额外交集，不改变主人桌面回合的既有行为。动态 MCP 工具默认不声明 `external_allowed`；若将来需要外部 MCP，必须先有独立的服务级权限规格。

### 7. 新工具默认安全

工具注册接口、插件适配器和能力目录序列化都要保留 `external_allowed`。未填写该字段的旧工具按 `false` 处理，旧配置迁移不会把工具自动提升为外部可用。

## Testing Decisions

测试最高使用入口到 Agent Runtime 的公开行为 seam：用受控渠道请求和测试模型产生真实工具调用，检查模型收到的 schema、执行结果、上下文范围和持久记录。只在需要替换时注入测试身份存储、消息查询、附件目录和外部 HTTP 服务，不测试私有字段或具体过滤函数名称。

至少覆盖以下外部行为：

1. 群友请求可以看到并调用 `web_search`，搜索失败仍返回真实错误，不扩大到本地工具。
2. 群友请求看不到 Shell、文件、浏览器、主人记忆和 MCP 管理工具；伪造这些工具调用时执行入口仍拒绝。
3. 群友调用消息查询时只能读取当前群或当前外部私聊，伪造其他 `thread_id`、`session_key` 或 `role_id` 不改变结果。
4. 群友调用成员查询时只能查询当前群，伪造群 ID 被宿主覆盖或拒绝。
5. 当前消息附件可以被读取，任意本地路径、其他消息附件和其他线程附件被拒绝。
6. 已配对主人在群里可以调用已启用的主人级工具，但模型输入不包含桌面、主人私聊或其他群原文。
7. 已配对主人私聊可以使用主人级工具；解绑后下一轮立刻按外部工具集合解析。
8. `tool_search` 的结果只包含当前回合可见工具，不泄露隐藏工具的 schema 或凭据。
9. 新注册工具未显式设置 `external_allowed` 时，群友 schema 和执行均不可用。
10. 普通角色级禁用、风险限制、批准拒绝和外部限制同时存在时，结果取最严格交集，并记录可解释的拒绝原因。

测试沿用现有 Agent Runtime、工具 schema、API 和能力快照测试约定；新增测试应优先放在已有工具解析/执行和多端入口测试 seam，不为每个工具复制一套独立权限框架。

## Out of Scope

- 不重新设计配对码、账号连接、渠道适配器或网页线程列表。
- 不实现新的操作系统沙箱、文件系统虚拟化、网络代理或数据流污染标签系统。
- 不让普通群友管理群旁听、群笔记、群上下文或角色设置。
- 不开放任意 Shell、文件、本地数据库、浏览器、桌面、屏幕、MCP、子 Agent 或账号投递能力。
- 不把群友请求自动升级为主人请求，也不因主人出现在群里而合并主人私聊和桌面历史。
- 不要求所有外部工具都只能是只读工具；图片生成等产品能力可以显式标记为外部可用，但必须继续受角色启用、额度和普通批准策略限制。
- 不改变自然群聊“未点名回合不调用工具”的现有规格；本规格只约束已经进入工具流程的请求。

## Further Notes

Shiori 的核心做法是“入口确认身份 + `ContextView` 限定上下文 + `external_allowed` 白名单”。它允许群友使用网页搜索、网页抓取和有限的消息/成员查询，同时在执行时继续收窄当前群、当前线程和当前附件范围。本规格采用这个最小形状，避免把多端权限提前扩展成完整的通用授权系统。

实现顺序建议为：先让能力解析和工具执行支持外部回合；再接入统一 `ContextView` 的线程/群/附件范围；最后为各渠道登记白名单工具并补入口回归测试。完成后再拆分具体渠道 Ticket，不把每个平台各自实现一套权限判断。

本规格与[多端会话规格](multichannel-conversations-spec.md)的关系是：总规格定义账号、线程、配对和渠道行为；本文定义其中的工具可见性、执行权限和作用域覆盖。两者冲突时，以更严格的可见范围和执行限制为准，并在实现前修正文档。
