# ADR-0030：固定 Grok Bot 的交流与接收回执

状态：已采纳；由 PR #257 合入。

最后核验：2026-10-28。

事实来源：[#241](https://github.com/sawaki-zexi/meido/issues/241)、已批准 Spec A4/A5/F13、[实现](../../backend/app/channels/grok/adapter.py)、[实际 Runtime 与 HTTP 验证](../../tests/python/test_grok_settings_api.py)。

## 决定

Grok 是第五类内置渠道，全局默认关闭。每角色只配置一个 HTTPS Webhook，固定外部身份与私聊目标，沿用原账号生命周期、目录、Runtime、线程和投递账本。不能经配对码变成主人。更换 Webhook 生成新对端身份、私聊和回程凭据，保留旧历史；原目标不能交给新 Bot。

回程使用仅监听 127.0.0.1 的认证入口和随包 PowerShell 客户端。连接文件置于当前系统用户私有目录，Routine 仅包含真实路径，不含密钥。启用和检查只报告本机入口状态，不自动向远端发任务。外部 Bot 已获得同机客户端执行许可是使用前提，本功能不授予完整工具权限。

按连接保存一个有界交流记录，负责父消息关联、双方合计额度和重复准入；它不是另一套投递队列。默认上限 12 条，可配置 2–100；最多 512 条收据，按完整且无待处理/发送中/未知消息的链淘汰。容量不足时拒绝新准入，事务回滚额度和淘汰操作。中断出站转为不确定，不重放；已持久准入的入站依赖原消息 ID 恢复并经过宿主去重。

明确拒绝未知、已淘汰、跨连接的父消息。Shiori 固定版本 `d149de7f` 的 `plugins/grok_bot/backend/exchange.py` 将未知父消息当新链；本决定按已批准 A5 收紧，避免旧回复重新获得交流额度。真正首发必须显式无父消息。

HTTP 200 只记录 `receiptKind=transport_acceptance` 和真实 HTTP 状态，保留空平台消息 ID，页面显示“已提交 Bot”。宿主仅允许 Grok 使用此回执，其他渠道仍须实际消息 ID。已接收文本可进入本线程后续语境，不表示对端已经完成任务。

## 兼容与取舍

交流记录是现有会话数据库中的新增表，不改写旧消息；角色删除一并清理，账号移除保留历史。只淘汰完整结束链意味着未知交流可能占满容量，此时明确拒绝新消息，不牺牲仍需去重的收据。去重只覆盖保留期，协议禁止重用消息 ID。

验证使用模拟 Webhook、真实本机 PowerShell 回程和实际角色 Runtime；没有真实 Grok 账号或收费模型验收。限额、入站 202 与重复 200、冲突拒绝和未知发送不重放按公开边界验证，不扩大偏门场景测试。
