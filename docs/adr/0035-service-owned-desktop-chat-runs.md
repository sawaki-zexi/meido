# ADR-0035：桌面聊天任务由服务持有，SSE 只负责订阅

状态：当前，已采纳；维护者批准 #293 的任务归属、刷新续接和确切 Stop 方案。
最后核验：2026-11-01。
事实来源：[#293](https://github.com/sawaki-zexi/meido/issues/293)、[规格](../specs/chat-responsiveness.md)、[生命周期合同](../reference/chat-run-lifecycle.md)、[行为测试](../../tests/python/test_chat_lifecycle.py)。

## 背景

原 `/messages` 的 SSE 生成器同时负责执行、保存和清理。连接断开会取消任务；拟人补充输入还会在生成器启动前等待旧任务，因此只删除断线 watcher 无法保证已接受的输入得到收尾。前端通过相同正文推测是否接受，也无法区分同文输入和新旧运行。

固定 Shiori `be6343d1deaa62c69f27d33654e77020b8f17c67` 的 [DesktopChatService](https://github.com/YinFengWindy/Shiori-Agent/blob/be6343d1deaa62c69f27d33654e77020b8f17c67/apps/backend/desktop_bridge/chat_service.py) 由服务持有 turn task；task 覆盖 previous/background 等待及最终清理，终态等角色所有权释放后发布。本决定适配这一归属和顺序，不复制 Electron JSONL bridge。

## 决定

1. `ChatRunService` 持有接受后的桌面任务，消费既有 `RuntimeManager`；不引入另一套模型或工具执行器。提交、订阅、停止是独立操作。旧 `/messages` 保留为同一提交和订阅的兼容组合。
2. **替代 ADR-0003 第 6 条的客户端断开即取消部分**：关闭或刷新网页仅解除订阅。显式 Stop、服务退出与既有来源失效仍取消，并等待已开始的工具回执和清理。provider/tool 超时和权限边界保持原合同。
3. 浏览器在请求前生成 `requestId`，对应固定 `runId`。现有 run 快照保存规范化请求摘要；重复提交只可恢复同角色、同输入的接受结果，不重复写用户消息。丢失接受响应后只读取或停止这个标识，不按正文或当前活动运行兜底。
4. 拟人输入先原子保存 `queued` run、用户行及占位行，再由同一个服务任务等待前驱。`queued` 只表示已接受、未执行；随后使用 RuntimeManager 原角色锁转为 `created`。SQLite 的文本状态无需结构迁移，既有 `created/running` 唯一索引继续限制实际执行。排队取消也等待前驱，不能取消或越过旧工具。
5. 服务保留有界当前工具投影和事件环；生产者不等待订阅者。超出事件窗口时明确发送快照信号，客户端从数据库读取当前消息和游标，再接续事件。最终消息仍以 SQLite 为准，不建永久逐 token 日志。
6. Runtime 结束不等于桌面任务结束。工具清理、附件处理、拟人多段发送完成之前，恢复投影仍是活动状态；终态事件延后到所有者完成收尾，避免界面恢复发送后撞上上一条清理。重复 Stop 等待同一任务，不反复取消 cleanup。
7. 前端的角色选择只决定所看订阅；旧连接、旧角色及旧 run 事件不能写入新视图。准备、摘要、模型请求、工具调用及收尾阶段由真实边界发布，沿用既有消息过程区。

## 取舍和恢复

网络中断后运行继续，用户需要显式 Stop 才停止已接受的回复。进程内投影不会跨重启保留；启动将 `queued/created/running` 收敛为失败并保留原输入、部分内容和工具记录，绝不重放模型或工具。跨进程自动续跑不在本决定范围。

事件环会舍弃中间增量，因此协议要求处理序号缺口，不能将 SSE 当成完整审计日志。当前文本从已有消息行读取，历史过程从既有工具记录投影；内存只持有有限事件和工具状态。边界与数值见生命周期合同。

角色删除同时检查 Runtime 和尚未清理的桌面所有者；queued 也阻止删除。全局活动查询优先返回正在执行的运行，避免桌面排队输入遮蔽渠道的当前运行。工具准入仍只接受已进入执行的 `created/running`，queued 不授予任何工具能力。
