# ADR-0029：沿用投递账本保存分段与固定期限

状态：当前

最后核验：2026-10-26

事实来源：[Issue #239](https://github.com/sawaki-zexi/meido/issues/239)、已获实施授权的 [Spec A4/F09/F11/F12](https://github.com/sawaki-zexi/meido/blob/chore/116-multichannel-parity-audit/docs/specs/shiori-multichannel-alignment-spec.md)、[投递实现](../../backend/app/channels/delivery.py)、[原线程决定](0009-multichannel-conversation-threads.md)。

## 问题

一条回复可能成为多个平台消息。只在最后记录一次结果，会丢失前段真实回执，也无法判断超时发生前哪些内容已经出现。宽泛的“失败后重发”会重复消息；引用、格式和频控各自重试又可能放大次数和延长旧任务。

## 决定

继续使用 `ChannelHost` 与原 `channel_delivery_attempts`。增加可空 `details_json`，兼容旧账本；不创建另一套出站队列，不从遗留 pending 自动恢复网络发送。逻辑目标、话题、来源和期限在宿主入口冻结，适配器在第一段发送前完成普通消息的分段计划。每次网络请求前写入在途状态，真实回执落盘后才发送下一段。

一个逻辑投递最多 120 秒，来源已有更早期限时取最早值。排队、限流、格式与引用后备共用期限；每段的这些恢复共用有限尝试次数。每个账号持有有界调度器，发送/编辑共享聊天冷却，typing 独立冷却，账号同时限频。等待时不持数据库事务，也不扩大 Runtime 角色锁。

仅明确未接受的白名单错误允许恢复。HTTP 权限拒绝和服务端不确定结果优先于正文中可能出现的恢复代码。取消引用保留原聊天和话题；不将 QQBot 被动回复转为主动消息。QQBot 的被动来源序号和保守配额预留也保存在同一账本，重建适配器不重置序号。

流式预览沿用同一来源许可、期限与账本。预览编辑记录最近确认内容；最终正文可确定时冻结分段，更新已有消息并发送尾部。每次编辑的有限重试共用原期限，未知结果终止后续编辑。临时占位文本不成为已说出的正文；最后正文先确认，再尝试关闭飞书卡片的流式显示。中途停止不改投新消息。

保持 `pending/sent/failed/uncertain` 四种顶层状态。分段包含回执、尝试次数、引用/格式后备标记及确认内容。原始消息不被裁剪；给模型和历史查询的投影只包含确认部分。手机展示部分已发送、未知段和未发尾部。普通平台必须取得真实消息 ID；未来 Grok 的 `transport_acceptance` 是另一种证据，不能借此放宽其他平台。

## 取舍

明确拒绝会消耗有限次数；QQBot 预留后即使没有派发，也不冒险回收序号。这可能少发，但不会因重启或未知结果重用来源配额。记录失败后停止尾部；磁盘持续不可写时无法承诺保存平台已返回的回执，因此不自动重放。

流式内容尚在生成，不能提前冻结未知尾部；因此区分预览与已冻结的最终分段。历史仅使用实际确认内容，不把完整生成结果当成完整送达。

错误白名单来自[一手资料核验](../research/channel-delivery-errors-2026-10-26.md)。Shiori 提供实体转换、逐段回执和限流的参照；其部分宽泛后备与网络重试不符合本规格的未知结果约束，未照搬。

## 验证

HTTP 边界替身覆盖 Telegram/飞书实际请求体与拒绝分类，账本测试覆盖前段回执落盘、未知停止、重启及配额。撤权测试覆盖等待后、令牌获取后和三平台流式更新；手机组件测试区分三类分段结果。未使用真实平台账号或付费模型，默认间隔不是吞吐实测承诺。
