本文说明在本地 Meido 中配置 Telegram、NapCat QQ、官方 QQBot 和飞书，并完成一次配对验证。平台后台的应用创建、权限申请和事件订阅仍以平台文档为准；本文不把模拟适配器测试当作真实账号验收。

## 准备

1. 启动 Meido，在“设置 → 插件 → 服务与连接 → 多端连接”的“平台总开关”中启用需要的平台；打开已保存角色的资料，切换到“账号”。
2. 为要接入的平台准备凭据。凭据由系统凭据库保存，不会回显到普通配置、公开 API 响应或日志。
3. 确认角色已经配置可用的模型连接。渠道收到触发消息后会复用该角色的 Runtime。
4. 外部平台需要能访问对应的本地连接：NapCat 使用 WebSocket，QQBot 使用 Gateway，Telegram 使用 Bot API 轮询，飞书常规接入使用长连接。

## 配置账号

角色资料的“账号”页按平台显示账号摘要和连接状态。点击某个平台后，在详情中填写连接信息、保存并连接；已配置账号的凭据表单通过“更改连接配置”展开。在线时可调整私聊、平台支持的群聊开关和屏蔽列表。

在“设置 → 插件 → 服务与连接 → 多端连接”的“平台总开关”中，每个平台明确显示“已启用／已暂停”，点击“暂停／启用”控制该平台的全部角色连接。角色资料的“账号”页也提供“平台总开关”直达入口。暂停保留账号各自的连接意愿；恢复时只连接原先开启的账号，重启后仍遵守平台暂停状态。单个账号的连接/断开在其详情管理。

- Telegram：填写 Bot Token。支持私聊和群聊；群回合仅在 @ 角色或回复角色消息时触发。
- QQ：Windows x64 默认在账号详情准备托管 NapCat，显示进度和二维码。按提示使用自己的 QQ 扫码，确认登录后连接账号；无需填写内部地址或令牌。需要已安装官方 QQ 9.9.31-49738，首次准备下载并校验 NapCat 4.18.28。其他环境或已有部署可展开手动连接入口，配置外部 NapCat/OneBot WebSocket 地址及可选 Access Token。两种方式都沿用私聊、群聊、@/回复触发、群成员目标和按群旁听。
- 官方 QQBot：填写 App ID、Client Secret 和 API 地址。当前只接收和发送 C2C 私聊，使用 Gateway 和流式回复能力。
- 飞书：填写 App ID、App Secret，并至少填写 Verification Token 或 Encrypt Key 其中一项。当前只处理私聊，支持媒体、引用信息和 CardKit 流式回复。

飞书默认使用 `lark-oapi` 长连接：Meido 在本地启动独立线程、维持连接并自动重连，常规运行不需要公开 HTTPS 回调服务。旧式 webhook 入口保留兼容；若部署仍使用 webhook，服务必须能接收飞书回调，并保留平台签名和令牌校验，请求路径为 `/api/channels/feishu/{account_id}/webhook`。同一账号应使用默认长连接入站，不要同时配置 webhook 入站。

保存配置会先暂停账号准入、排空已接受的事件和发送、停止旧连接，再保存并启动新连接。失败时会恢复旧配置；切换期间可能短暂没有连接。暂停期间收到新消息时，原连接会告知“尚未处理，请重发”；收到提示后等连接恢复再发送。

## 完成主人配对

1. 在“设置 → 我的身份”点击“生成配对码”，可复制代码并查看剩余时间；无需先选择角色。全应用同时只有一个待用码，默认 10 分钟有效，只能成功使用一次；生成新码或重启 Meido 会使旧码失效。
2. 从任一已连接角色账号的私聊发送配对码本身，或使用 `/pair <配对码>`；生成码的网页位置不限定接收角色或平台。
3. 配对成功后，Meido 保存该私聊身份、账号和授权起点，并发送“配对成功”确认。配对命令不会进入角色历史，也不会触发模型回合。
4. 配对前的消息不会因为后来配对而获得主人上下文。Telegram/NapCat 一次配对会在该平台所有角色账号识别主人；飞书/QQBot 的应用内用户 ID 只在配对的应用账号识别。

“我的身份”统一显示全部平台及应用的已配对主人绑定，可点击“刷新绑定”或“解绑”。解绑撤销主人权限、私聊共享和相关主动提醒目标，重新配对不会恢复已取消的提醒订阅；聊天和投递记录保留。移除账号清理该账号作用域身份和私聊目标，平台范围身份仍供其他账号识别。全局主人身份不会跨角色共享原始历史或记忆。

## 群触发与旁听

Telegram 和 NapCat 的群消息只有在结构化 @ 或回复角色消息时才会启动模型回合。正文中写“@角色”而没有平台 @ 元数据，不会被当作触发条件。

NapCat 旁听按账号和群单独开关。独立手机会话页移除后，网页不再提供群级设置入口，既有配置仍生效；维护时使用宿主接口：

1. `GET /api/roles/{role_id}/channels/accounts/{account_id}/groups` 读取已观察或发现的群。
2. 向 `/api/roles/{role_id}/channels/accounts/{account_id}/groups/{chat_id}/listening` 发送 `PUT {"enabled": true}` 开启该群旁听；`false` 暂停。未触发消息保存在独立旁听记录，不回复、不启动角色回合或工具，也不下载消息或引用附件。
3. `GET /api/roles/{role_id}/channels/threads/{thread_id}/listening` 查看设置及计数，`.../listening/messages` 分页读取记录。默认每群每日 200 条，宿主保留全局默认与当前群覆盖接口；超过上限后的消息只留内存最近 30 条作为当前群近期上下文，重启后不恢复。
4. 向第 2 步路径的 `/messages` 发送 `DELETE` 只清理该群旁听消息，正常的 @/回复回合和角色回复保留。独立后台整理每批 50 条，跨天余量由每 30 分钟扫描收尾。

Telegram 不提供旁听开关；官方 QQBot 和飞书当前没有群聊能力。群友旁听只更新当前群档案，可信主人发言可形成主人事实；不同群不会自动共享原始消息或成员档案。

## 网页查看

侧栏不再提供“手机会话”入口或独立渠道会话管理页面。账号连接在角色资料 → 账号管理，日常聊天在对应外部平台进行。

在角色记忆面板点击渠道记忆的“定位到消息”，会打开只读“记忆来源”弹窗，核验线程归属后跨页定位并标记原文；旁听记忆读取当前群的独立旁听来源。弹窗保留图片、文件、引用、提及和投递回执，不显示账号、群旁听或提醒目标管理控件，也不订阅实时会话消息。关闭后仍留在原记忆页。

来源读取不依赖账号或会话目录，旧线程仍可通过角色归属校验打开。删除、清理或无法自动定位的来源会明确提示，不会跳转到其他角色的消息。

账号、联系人和群头像在后台获取并缓存七天，失败保留旧头像，不阻塞收发。网页不会替代 Telegram、QQ、QQBot 或飞书发送消息，不复现平台全部原生样式，也没有未读计数。实际外部发言从相应平台完成。

## 主动目标与工具

角色在桌面主人回合和已配对主人渠道回合中可以使用渠道工具：

1. `account_list` 查看当前角色账号及能力。
2. `account_targets` 查看某账号已经观察或发现的私聊、群或群成员目录。返回的 `target_id` 是不透明目录 ID，不要自行拼接平台 chat ID。
3. `account_send` 向目录目标发送文本或角色附件。每条最多 4 个附件，单个附件最多 10 MB，附件必须属于当前角色。

向群发送时，`mention_ids` 只能填写该群已观察或平台已发现的成员 ID；私聊和不支持提及的平台会明确拒绝。Telegram 群目录还会返回 `topicIds`，可用 `message_thread_id` 选择已观察到的话题。普通群发送不自动选择最近话题，渠道回复则保留触发消息自己的话题；未知话题 ID 会在平台请求前被拒绝。

渠道回复固定发送回产生当前回合的线程。外部访客回合不能选择任意账号或第三方目标，只能把 `target_id` 设为 `owner`，由宿主使用当前账号解析已配对主人私聊。群工具也按当前角色和群线程校验；访客只能查询当前群已观察到的成员，群笔记/摘要和旁听设置属于主人能力。

桌面回合仍使用桌面 transcript，可读取已配对主人私聊的授权片段；角色已配置渠道账号时才启用渠道工具，实际发送要求账号可用。渠道访客和群原文不会自动进入桌面上下文。主人私聊完成后共同维护主人近期/历史 Markdown；读取前重验绑定，避免解绑后仍注入旧私聊原文。

普通对话的 `message_push` 仅向当前角色自己的桌面对话推送，需在角色基础工具中显式开启；无需任何渠道账号。使用 `channel=desktop, chat_id=owner` 或 `user`，可附文本、当前角色的 `image`/`file` 或 `attachments` ID。已配对主人渠道回合也只能投到此角色桌面，访客拒绝。外部发送统一使用 `account_send`，不再通过 push 选择外部目标；见[桌面推送契约](../reference/desktop-push.md)。

## 待办提醒投递到手机

网页不再提供会话级提醒目标配置入口，既有选择继续生效。维护时通过以下宿主接口显式配置：

1. 在对应渠道私聊完成主人配对。
2. `GET /api/roles/{role_id}/channels/push-targets` 查看该角色可用的已配对主人目标。
3. 向 `/api/roles/{role_id}/channels/accounts/{account_id}/push-target` 发送 `PUT {"targetId": "<目录目标 ID>"}`。每个账号最多选择一个目标，可同时为不同渠道显式选择目标；系统不会根据最近活跃渠道猜测目的地。
4. 此角色负责的待办提醒仍先保存到桌面，再投递到已选择渠道；消息与投递状态保存在对应线程。
5. 发送 `PUT {"targetId": null}` 停止该账号后续提醒。解绑主人或删除账号也会取消目标的授权，停用账号时不会向其他渠道自动改投。

同一个提醒在同一账号只尝试一次。平台发送失败或结果不确定不会影响桌面提醒，也不会触发自动重复发送。提醒投递沿用渠道账本，保留来源 session、提醒事件、实际适配器连接代次和平台回执；`account_send` 另记录来源回合和工具调用编号。

## 不确定投递的人工核验

投递状态包括 `pending`、`sent`、`failed` 和 `uncertain`。网络超时、连接中断或平台可能已经接受请求时，系统会记录 `uncertain`，不会自动重发。服务重启时遗留的 `pending` 也会转为 `uncertain`。

发现不确定投递时：

1. 通过 `/api/roles/{role_id}/channels/deliveries` 查看 `uncertain` 记录和平台消息编号（若平台返回）；记忆来源弹窗也会展示原消息的投递状态。
2. 到对应平台确认目标聊天是否已经收到内容，避免重复发送。
3. 需要审计时读取渠道投递接口 `/api/roles/{role_id}/channels/deliveries`，记录 `attemptId`、账号、目标聊天、状态、平台消息编号和错误摘要。
4. 确认未送达后，由主人在对应平台或通过新的明确工具调用重新发送；不要把 `uncertain` 直接改写为确定失败。

网页目前没有独立的投递诊断或重试面板。投递账本保留结果，平台侧确认仍是人工步骤。

## 常见失败

- 账号显示“凭据缺失”：重新填写必需凭据并保存。系统不会把凭据回退写入普通数据库。
- 群消息没有回复：检查账号允许群聊、平台权限以及消息是否带有结构化 @ 或回复元数据。
- NapCat 旁听没有记录：通过群目录接口确认群已被观察或发现、账号已启用且群旁听开关打开。
- 飞书账号无法启用：确认已配置 Verification Token 或 Encrypt Key 至少一项。若兼容 webhook 返回校验错误，再检查原始请求体和签名头；默认长连接故障则检查连接线程和 `lark-oapi` 依赖。
- 连接配置保存失败：旧连接会被恢复；先检查平台凭据和网络，再重新测试，不要并行启动同一账号的多个连接。

托管 QQ 出现准备失败时，先按页面提示检查 Windows x64、官方 QQ 版本与网络，再重试。二维码过期可刷新；取消登录会停止临时进程。断开或暂停保留登录数据供恢复，移除托管账号会清理其私有运行数据，不操作外部模式的 QQ/NapCat。真实二维码扫码与收发仍需在目标环境验证。
