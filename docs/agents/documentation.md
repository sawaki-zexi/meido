# 文档规范

本项目采用 Docs-as-Code：文档和代码一起版本控制、一起审查。每类文档只承担一种主要用途，避免把产品说明、技术决定和操作步骤混在一起。

## 文档分类

| 位置 | 用途 |
| --- | --- |
| `README.md` | 项目介绍、安装和最短上手路径 |
| `CONTEXT.md` | 稳定的领域词汇、对象关系和业务边界 |
| `docs/agents/` | Agent 和维护者必须遵守的协作规则 |
| `docs/specs/` | 已确认功能的完整规格、用户流程和验收方向 |
| `docs/adr/` | 有真实取舍且难以逆转的架构决定 |
| `docs/research/` | 外部资料、源码核验、实验和选型过程 |
| `docs/handbook/` | 如何完成某项开发、配置或验收任务 |
| `docs/reference/` | 稳定接口、事件、配置和数据契约 |

## 写作规则

- `CONTEXT.md` 不写文件路径、框架、数据库或 API 等实现细节。
- ADR 记录“为什么选择”，不替代 Spec 或操作手册；决定改变时保留旧 ADR，并新增替代记录。
- Research 记录证据和不确定性；研究结论真正落地后，把稳定事实回写到 Spec、Reference 或领域文档。
- Spec 描述问题、解决方案、用户故事、范围、架构决定和测试决定；不要把每个开发 Ticket 的步骤都塞进去。
- Ticket 只描述一个可独立验证的用户结果、验收标准和阻塞关系，详细方案由 Agent 的实现计划承接。
- 手册按完成任务的顺序写，包含准备条件、步骤、验证和常见失败；不要重复整套架构背景。
- Reference 以代码、Schema 或测试为事实来源，完整记录字段、事件、错误和兼容性。

## 状态和证据

需要长期维护的文档应在标题或开头标明：

- `状态：当前`、`草案`、`已废弃` 或 `已被替代`
- `事实来源：`相关源码、测试、Schema、ADR 或外部资料
- `最后核验：`日期或提交

明确区分：

- **已提取**：源码或测试直接证明的事实
- **推断**：根据多个事实得出的解释
- **计划**：尚未实现的目标设计

文档与源码冲突时，以源码和测试为准，并在同一变更中修正文档。新增或移动文档后检查相对链接；不要留下指向不存在文件的链接。
